# 数据清洗规则清单

> T3 阶段 3 产出，对应《数据清洗基本流程-操作SOP》第 5 节。
> **每条规则都挂在 [02_issues.csv](02_issues.csv) 的实测问题编号上**，或挂在 SOP 明文要求的统一动作上——
> 没有依据的规则不写。执行见 `bigdata/spark/cleaning.py`，校验见 `validation.py`。

## 总原则（SOP 第 5 节）

- 能按确定规则修正的，自动修正并**记录旧值新值**
- 无法确定但仍有价值的，**保留并标记待核**
- 真实异常不因数值极端而自动删除
- **删除是最后手段**，必须记录数量、原因和样例
- 关键字段（业务主键、金额、目标变量）不套用通用规则

## R001 · 伪缺失归一

| 项 | 内容 |
| --- | --- |
| 作用对象 | ODS 全表所有字符串列 |
| 检测条件 | `trim(值) ∈ {'', 'NULL', 'null', 'N/A', 'n/a', '-', 'None', 'nan'}` |
| 处理动作 | 归一为真正的 NULL |
| 处理依据 | SOP 6.1 第 1 条 |
| 影响评估 | 探查阶段未发现伪缺失，预计 0 行；**规则仍要执行**，它保障的是重跑时新数据进来也干净 |
| 异常去向 | 无 |
| 验证方式 | 清洗后全表不存在上述取值 |

## R002 · 类型转换，失败记录不静默丢弃

| 项 | 内容 |
| --- | --- |
| 作用对象 | `t_order`(order_id/user_id/pile_id/station_id/status/price/kwh_x100/amount)、`t_pile`(pile_id/station_id/type/status/power/online)、`t_station`(station_id/price/status) |
| 检测条件 | 转换为 int/double 后为 NULL，但原值非 NULL |
| 处理动作 | 主体转换为强类型；**失败行整行写入待核清单**，不置空 |
| 处理依据 | SOP 6.2「类型转换失败的值不要静默变为空值，应输出失败记录与原始值供复核」 |
| 影响评估 | 探查显示各列取值规整，预计 0 行失败 |
| 异常去向 | `bigdata/quality/pending/type_cast_failed.csv` |
| 验证方式 | DWD 各列类型符合预期，且失败清单行数 + 成功行数 = ODS 行数 |

## R003 · 时间统一为 `yyyy-MM-dd HH:mm:ss`

| 项 | 内容 |
| --- | --- |
| 作用对象 | `t_order` 四个时间列、`t_pile_log.create_time`、`t_pile.last_heartbeat` |
| 检测条件 | 按该格式解析失败且原值非 NULL |
| 处理动作 | 转 timestamp；解析失败写待核 |
| 处理依据 | SOP 6.2、6.8；CLAUDE.md 第 2.1 节时间口径 |
| 影响评估 | 一阶段写入时即为该格式，预计 0 行失败 |
| 异常去向 | 同 R002 |
| 验证方式 | 时间列非空行数与清洗前一致（**不允许因转换而新增缺失**） |

## R004 · 金额与电量保持整数，禁止浮点

| 项 | 内容 |
| --- | --- |
| 作用对象 | `t_order.amount`(分)、`t_order.price`(分/度)、`t_order.kwh_x100`(电量×100) |
| 检测条件 | — （这是**禁止性**规则，不是修正规则） |
| 处理动作 | 一律转 `bigint`；派生指标用整数运算，仅展示层除 100 |
| 处理依据 | CLAUDE.md 5.2 第 7 条；SOP 6.2「金额使用定点表示，避免浮点误差」 |
| 影响评估 | 全部 8292 行 |
| 异常去向 | 无 |
| 验证方式 | DWD schema 中三列均为整数型；营收合计与 ODS 直算逐分相等 |

## R005 · 码表归一（状态与类型转中文标签）

| 项 | 内容 |
| --- | --- |
| 作用对象 | `t_order.status`、`t_pile.status`、`t_pile.type`、`t_user.status`、`t_pile_log.event` |
| 检测条件 | 取值不在码表内 |
| 处理动作 | 按码表新增标签列（**保留原始码值列**，不覆盖）；越界值标为「未知」并进待核 |
| 处理依据 | SOP 6.6「使用码表统一同义表示」；码表取自 CLAUDE.md 第 6 节与 `db-schema.sql` 注释 |
| 影响评估 | 探查显示枚举全部合法，预计 0 行越界 |
| 异常去向 | `pending/enum_out_of_range.csv` |
| 验证方式 | 标签列无「未知」，且各标签计数与原码值计数逐一相等 |

## R006 · 非法手机号：标记待核，**不删不改**　← Q001

| 项 | 内容 |
| --- | --- |
| 作用对象 | `t_user.phone` |
| 检测条件 | `NOT RLIKE '^1[3-9]\d{9}$'` |
| 处理动作 | 新增 `phone_valid=false` 标记，**保留原行原值** |
| 处理依据 | SOP 第 5 节「关键字段的缺失、冲突或重复不得用通用规则一刀切」。手机号是用户端登录主键（[说明书] 1.4 免密登录），删除会连带毁掉其关联数据；改写则是**凭空编造**业务事实 |
| 影响评估 | 1 行（`12345678901`），占 t_user 20% |
| 异常去向 | `pending/invalid_phone.csv` |
| 验证方式 | 待核清单恰好 1 行；`t_user` 行数清洗前后均为 5 |

## R007 · 冻结用户的历史订单：保留　← Q002

| 项 | 内容 |
| --- | --- |
| 作用对象 | `t_order` × `t_user.status=1` |
| 检测条件 | 订单所属用户当前为冻结态 |
| 处理动作 | **不处理**，仅在质量报告中说明口径 |
| 处理依据 | 冻结是**后置管理动作**（[说明书]：管理员可手动冻结解冻），历史订单发生在冻结之前，本就应当存在。按「一致性冲突」删除会抹掉 4136 笔真实交易，是典型的误删 |
| 影响评估 | 4136 行（49.88%），**零改动** |
| 异常去向 | 无 |
| 验证方式 | 清洗前后订单数均为 8292 |

## R008 · `t_pile_log` 空字段剔除，设备维度重新定义　← Q004 / Q005 / Q006

| 项 | 内容 |
| --- | --- |
| 作用对象 | `t_pile_log.old_status`(缺失 100%)、`new_status`(缺失 98.67%)、`event=4` 故障上报(0 行) |
| 检测条件 | 缺失率 > 50%；某 event 取值无任何记录 |
| 处理动作 | ① 两列**不进 DWD**（SOP 6.3：`>50%` 评估字段信息量，可剔除）；② 保留 `event` 与 `create_time`，设备维度改做**事件类型与时序分布**，不做状态流转 |
| 处理依据 | 1763 条「状态变更」既不记变更前也不记变更后，承载不了任何分析；故障上报 0 行，则「故障分析」在数据层面是空的 |
| 影响评估 | 剔除 2 列；**PHASE2-PLAN 的 D8 维度必须改写**——1800 行里真正有内容的仅 37 条（上线 27 / 离线 2 / 远程重启 8） |
| 异常去向 | 无（列级剔除，行不动） |
| 验证方式 | DWD 无这两列；报告中记录 D8 维度的变更及原因 |

## R009 · 空表与低量表不纳入分析　← Q007–Q011

| 项 | 内容 |
| --- | --- |
| 作用对象 | `t_station_review`(0)、`t_wallet_tx`(1)、`t_admin_oplog`(3)、`t_carbon_report`(5)、`t_load_forecast`(18) |
| 检测条件 | 事实表行数为 0 或 < 100 |
| 处理动作 | 仍导入 DWD（**不删数据**），但在维度设计中排除；`t_load_forecast` 仅用于快照类展示 |
| 处理依据 | SOP 第 5 节「删除是最后手段」。数据量不足是**分析范围问题**，不是数据错误，不该用删除来解决 |
| 影响评估 | 0 行被删 |
| 异常去向 | 无 |
| 验证方式 | DWD 表数与 ODS 一致；质量报告列明被排除的维度及原因 |
