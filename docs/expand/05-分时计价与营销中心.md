# 05 · 分时计价与营销中心

## 1 文档用途

本文是扩展模块 05 的任务规格。技术底座、命令字分段、单位口径、接缝规则见 [00-扩展功能模块实施路径推荐.md](00-扩展功能模块实施路径推荐.md) 第 4、5 节；**凡本文第 5 节与 00 第 4 节冲突，以 00 为准**。

本模块把「一站一价」升级为「分时段价格 + 一种满减券」。它直接改动**计费与结算**这条核心链路，是全部扩展中**唯一必须动核心业务口径**的模块，因此建议由 **L2** 认领——金额、事务边界、订单状态都是他的本职，交给别人做完还得他逐行复核。

**先做不带优惠的分时计价，再接一种满减券。** 会员、积分、多活动叠加一律不做。

## 3 业务流程

### 3.1 价格发布

1. 管理员为某站点创建价格草稿，填写生效时间及若干半开区间 `[startMinute, endMinute)`。
2. 服务端校验同一天内的区间从 `00:00` 连续覆盖到 `24:00`，不得重叠、留空或出现负价格。
3. 管理员发布草稿。服务端生成不可变版本，并保证同一站点、同一时刻只能命中一个已发布版本。
4. 已发布版本不得原地修改。变价必须复制为新草稿并发布新版本；旧版本只允许到期或被未来版本接替。

### 3.2 订单计价

1. 用户查看站点时，服务端返回当前有效价格及未来时段，不由 Qt 客户端拼接数据库数据。
2. 订单从 `RESERVED` 进入 `CHARGING` 时，服务端选择有效价格版本，并写入订单价格快照。没有有效版本时应拒绝开始充电或使用系统明确配置的兼容固定价，禁止默认为零元。
3. 订单结束充电后，服务端依据起止时间、充电量和快照切分费用。优先使用周期电表读数；只有总电量时，按各时段持续时间比例分摊，并在明细中记录 `TIME_PRORATED` 降级口径。
4. 订单进入 `PENDING_PAYMENT` 后，用户请求账单预览。服务端返回电费、服务费、优惠和应付金额，但预览不等于支付成功。
5. 用户支付时只提交订单、所选优惠券和幂等键。服务端重新计算并在一个事务内扣款、核销优惠券、写流水和推进订单为 `PAID`。

### 3.3 优惠券

1. 管理员创建并启用一种“满 X 分减 Y 分”的优惠券模板，可设置领取期限、使用期限、适用站点、门槛和发行量。
2. 用户领取后得到一张 `AVAILABLE` 优惠券；重复领取和超发必须由数据库约束与事务共同阻止。
3. 用户选择优惠券进行结算时，服务端校验订单归属、适用范围、门槛和有效期，再将券锁给该订单。
4. 支付成功后券转为 `USED`；订单取消、锁定超时或支付回滚后恢复为 `AVAILABLE`，但已过期或已撤销的券不得恢复可用。

## 4 状态、金额与不可破坏约束

### 4.1 状态定义

- 核心订单状态只使用既有的 `RESERVED`、`CHARGING`、`PENDING_PAYMENT`、`PAID`、`CANCELLED`，不得新增 `DISCOUNTED`、`REFUNDED` 等不兼容值。
- 价格方案状态：`DRAFT -> PUBLISHED -> EXPIRED`。仅 `DRAFT` 可编辑；`PUBLISHED` 内容不可变。
- 优惠券状态：`AVAILABLE -> LOCKED -> USED`，以及终态 `EXPIRED`、`REVOKED`。`LOCKED` 必须记录 `locked_order_id` 和锁定到期时间。
- 营销活动首版可不单独建状态机；若仓库已有活动实体，则沿用 `DRAFT -> ACTIVE -> PAUSED -> ENDED`，不要复制一套同义状态。

### 4.2 金额与计量规则

- 钱包余额、满减门槛、优惠金额、应付金额和流水金额统一使用 64 位整数“分”，字段建议以 `_cents` 结尾。
- 充电量使用整数 Wh；费率使用高精度整数，例如“微元/千瓦时”，不得以 `float` 或 `double` 直接完成结算。
- 计算时先在高精度整数域累加各分段原始金额，执行溢出检查，再按统一规则四舍五入到分。舍入应只在规定层级发生，并保存 `rounding_adjustment_cents`，不得在客户端重复舍入。
- 必须满足：`original_amount_cents - discount_amount_cents + rounding_adjustment_cents = payable_amount_cents`，且各金额不得为负；优惠额不得超过原价。

### 4.3 不可破坏约束

- 最终金额只能由服务端基于订单事实和价格快照计算，客户端提交的展示金额不可信。
- 历史订单永远读取自身快照和费用明细；后续改价不得改变历史账单。
- 同一站点同一时刻只能命中一个已发布价格版本，单个版本的日内时段必须完整且不重叠。
- 一个优惠券实例最多核销一次，同一时刻最多锁给一个订单。
- 支付必须原子完成。余额、优惠券、费用明细、支付流水和订单状态不能出现部分成功。
- 重复支付、Socket 超时重试和重复点击必须依靠幂等键返回同一结果，不得二次扣款或二次核销。
- 原有固定价格数据需要迁移成兼容价格版本，或保留明确的只读兼容分支；不得让旧站点突然无法充电。

## 5 建议架构、数据、协议与 UI

### 5.0 技术路线校准（对齐真实仓库）

| 原文档设计 | **校准后落地** | 为什么 |
| --- | --- | --- |
| 单价用「微元每千瓦时」 | **一律 分/度（`INTEGER`）**，与已冻结的 `t_station.price`、`t_order.price` 同单位 | 152 分/度的精度足够；第二种单价单位是纯风险，见 00 第 4.5 节 |
| 电量用 Wh | **`kwh_x100`（度 × 100 的整数）**，与 `t_order.kwh_x100` 一致 | 同上 |
| `order_price_snapshot` 表（订单唯一） | 保留，命名 **`t_price_snapshot`**，`order_id` 唯一。快照必须存**足以离线复算**的完整时段规则 JSON，不能只存一个 `plan_id` 外键 | 价格方案会被改版；只存外键则历史订单无法复算，对不了账 |
| 「若既有订单表已有原价/应付字段则复用」 | 实测 **`t_order` 只有一个 `amount`（应付金额，分）**，没有原价列。MVP：`t_order.amount` 继续表示**实付**（语义不变），原价与优惠额落 `t_price_snapshot` / `t_price_discount`。要给 `t_order` 加 `origin_amount` 列 → **走 CR**，未批前按前述方案做 | 改冻结表要 L2 在 `db-schema.sql` 落笔；`amount` 语义一旦变，2301/2302 营收统计与大屏快照全部要复核 |
| 跨时段电量切分 | 用 `kwh_x100` **整数**切分，各段之和**必须精确等于**订单总量，余数（不足 1 个 0.01 度的部分）**归入最后一段** | 浮点切分必然出现分段和 ≠ 总量，答辩现场对账就崩 |
| 金额舍入 | 每段 `段电量 kwh_x100 × 段单价(分/度) / 100`，**每段先按四舍五入取整到分，再求和**；口径写进快照，复算必须一致 | 「先求和后舍入」与「先舍入后求和」差一分钱，两端会各算各的 |
| 支付请求含金额 | **金额一律服务端算**，请求只带 `orderId` / `couponId` / `reqId`。客户端传来的任何金额一律忽略 | 原文已如此要求，保留并强调 |
| 「可重复迁移」 | `docs/db-schema-ext-05.sql`，见 00 第 4.4 节 | 仓库无迁移框架 |
| 新增「余额不足 / 订单状态冲突」错误码 | **复用 `ERR_BALANCE_NOT_ENOUGH(2004)` / `ERR_ORDER_STATUS(4003)` / `ERR_ORDER_SETTLED(4004)`** | 见 00 第 4.3 节 |

### 5.1 服务端架构

按现有工程分层映射以下职责，不要求机械创建同名类：

- `PricingRuleService`：选择有效价格版本、校验时段完整性和发布冲突。
- `BillingEngine`：读取订单事实与快照、切分电量、输出确定性的费用明细；应尽量实现为无 UI、可单元测试的纯业务组件。
- `CouponService`：领取、资格校验、锁定、释放和核销。
- `SettlementService`：协调订单、计价、优惠券、钱包和支付事务。
- Repository/DAO：统一访问 SQLite；Qt 界面和 Socket handler 不得直接拼 SQL。

建议调用链：`Qt/Web -> Socket 网关 -> 鉴权/校验 -> 业务服务 -> Repository -> SQLite`。

### 5.2 数据模型

在适配现有命名规范后，至少需要以下数据；所有外键、唯一约束和索引通过幂等的扩展建表脚本创建：

| 建议实体 | 关键字段或约束 |
| --- | --- |
| `pricing_plan` | 站点、版本号、状态、生效/失效时间、创建人；`station_id + version` 唯一 |
| `pricing_period` | 方案、开始分钟、结束分钟、电价、服务费；同方案区间不得重叠 |
| `order_price_snapshot` | 订单唯一、价格方案版本、完整规则 JSON 或规范化快照、算法版本、创建时间 |
| `order_fee_segment` | 订单、区间、电量 Wh、电费分、服务费分、小计分、分摊口径 |
| `coupon_template` | 门槛分、优惠分、发行上限、领取/使用时间、适用范围、启用标志 |
| `user_coupon` | 用户、模板、状态、锁定订单、锁定到期时间、核销时间；券实例主键唯一 |
| `billing_discount_line` | 订单、优惠来源、优惠分、说明；首版每单至多一张券 |

若既有订单表已有原价、应付价字段，应复用或以最小迁移补齐，不要新建第二张订单主表。价格快照应保存足以离线复算的数据，不能只保存一个可能被删除的外键。

### 5.3 Socket 协议

动作名应适配仓库已有枚举和消息 envelope。建议覆盖以下语义：

| 方向 | 逻辑动作 | 核心输入/输出 |
| --- | --- | --- |
| 管理端 | 创建/更新价格草稿 | 站点、生效时间、时段列表；返回草稿版本和校验结果 |
| 管理端 | 发布价格版本 | 方案 ID、期望版本；返回已发布版本和生效时间 |
| 用户端 | 查询有效价格 | 站点、查询时刻；返回版本和时段列表 |
| 用户端 | 获取账单预览 | 订单 ID、可选券 ID；返回费用分段、优惠资格、应付分和计算版本 |
| 用户端 | 查询/领取优惠券 | 分页条件或模板 ID；返回用户券实例 |
| 用户端 | 支付订单 | 订单 ID、可选券 ID、`idempotencyKey`；金额不得作为可信输入 |

所有响应沿用统一错误结构。至少区分：无有效价格、价格时段非法、价格版本冲突、优惠券不可用、优惠券已锁定、余额不足、订单状态冲突、重复请求和服务端计算失败。服务端从会话身份确定用户与权限，不信任请求中的用户 ID 或管理员角色。

### 5.4 UI 范围

- 用户端：站点详情展示当前电价、服务费和全天价格时间轴；待结算页展示分段费用、原价、优惠券选择和实付金额；支付结果展示钱包流水关联号。
- 管理端：价格方案列表、草稿编辑、全天覆盖校验、版本发布、历史版本查看；优惠券模板创建、启停、发行和领取/核销统计。
- Web 大屏不是 MVP 阻塞项；若已有统一统计接口，可追加峰平谷订单量、原价、优惠额和实付额。页面不得直连 SQLite，也不得散落演示硬编码。
- 首版不实现会员和积分入口，避免出现不可用按钮。

## 6 顺序实施步骤

必须按顺序推进。每一步通过验证后再进入下一步；若仓库已有等价能力，应复用并记录差异，而不是重复实现。

### 步骤 1：仓库审计与变更设计

- 产出：核心订单/钱包状态迁移图、当前结算调用链、拟改文件清单、扩展建表脚本草案、兼容旧固定价方案。
- 验证：现有核心测试保持通过；能明确指出订单何时保存价格快照、何处开启结算事务以及 Socket 重试如何处理。

### 步骤 2：价格数据与发布服务

- 产出：价格方案和时段建表、DAO/Repository、草稿增改查、发布校验、旧固定价格兼容逻辑、可重复演示数据。
- 验证：覆盖全天、缺口、重叠、跨零点表达、负价格、重复版本和生效冲突测试；迁移可在空库和既有数据库上各执行一次。

### 步骤 3：确定性计费引擎

- 产出：价格选择器、订单快照、跨时段切分算法、按时长降级分摊、费用分段与统一舍入实现。
- 验证：给定同一订单事实多次计算结果逐字段一致；覆盖单时段、跨两时段、跨零点、零电量、边界时刻和大数溢出测试。

### 步骤 4：接入结束充电与基础结算

- 产出：结束充电后生成/读取账单、服务端支付重算、钱包扣款、支付流水、订单 `PENDING_PAYMENT -> PAID` 的单事务实现和幂等处理。
- 验证：成功支付、余额不足、重复支付、事务中途失败、Socket 超时重试均符合不变量；关闭营销开关时仍可按分时价格支付。

### 步骤 5：接入单一满减券

- 产出：券模板、领取、查询、资格判断、锁定、超时释放、核销和优惠明细；首版固定优惠顺序为“基础费用 -> 满减券”。
- 验证：并发领取不超发、一券不能锁两单、未达门槛不可用、过期/跨站不可用、支付回滚后正确释放、重复请求不重复核销。

### 步骤 6：完成 Qt 管理端和用户端

- 产出：价格编辑与发布界面、站点价格展示、账单分段、券选择和支付结果；所有界面只调用服务端协议。

### 步骤 7：回归、文档与演示数据

## 8 Definition of Done

- [ ] 管理员能创建、校验和发布一个完整的站点分时价格版本，已发布版本不可编辑。
- [ ] 订单开始充电时保存不可变价格快照，跨时段订单能生成可追溯费用分段。
- [ ] 金额只使用整数分或高精度整数计算，并有统一舍入、溢出和金额守恒测试。
- [ ] 用户能领取并在满足条件时使用一张满减券；锁定、释放和核销均具备并发保护。
- [ ] 支付事务原子推进钱包、流水、优惠券、费用明细和订单，重复请求不重复扣款。
- [ ] 未修改或扩展核心订单状态枚举；旧固定价站点和无券结算仍能工作。
- [ ] 用户端和管理端走 Socket 服务，不直接访问 SQLite 或自行计算最终金额。
- [ ] 单元、集成、协议和核心回归测试通过，关键失败路径有测试证据。
- [ ] 空库初始化、既有库上重复执行 ext 脚本、演示数据和端到端演示步骤可重复执行。
- [ ] 交付说明列出改动文件、扩展建表脚本、协议变化、运行命令、测试结果和未实现非目标。

## 9 风险与降级

| 风险 | 首选处理 | 无法按期完成时的降级 |
| --- | --- | --- |
| 周期电表数据不足 | 保存各采样点并按真实增量切分 | 按时长比例分摊，明细标记 `TIME_PRORATED` |
| 既有固定价耦合较深 | 将固定价映射为全天单时段版本 | 保留只读兼容适配器，但结算仍生成快照 |
| 券并发锁定复杂 | 使用条件更新、唯一约束和短事务 | MVP 暂停“提前选择”，仅在支付事务中原子占用一张券 |
| UI 工期不足 | 优先完成服务、协议和最小表单 | 大屏统计延期，保留 Qt 基础发布与账单界面 |
| 组合营销膨胀 | 固定一种满减券和唯一优惠顺序 | 会员、积分、叠券全部列入后续，不留半成品入口 |
| 价格发布冲突 | 发布时查询重叠有效期并使用事务 | 首版要求新版本从旧版本结束时生效，不支持预约未来多版本 |

任何降级都不能取消价格快照、服务端最终计费、整数金额、事务原子性、幂等支付或核心状态兼容这些底线。
