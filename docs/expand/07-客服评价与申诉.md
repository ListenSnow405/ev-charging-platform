# 07 · 客服评价与申诉

## 1 文档用途

本文是扩展模块 07 的任务规格。技术底座、命令字分段、单位口径、接缝规则见 [00-扩展功能模块实施路径推荐.md](00-扩展功能模块实施路径推荐.md) 第 4、5 节；**凡本文第 5 节与 00 第 4 节冲突，以 00 为准**。

**本模块有一半已经躺在冻结的 schema 里**：`t_station_review`（站点评价，含 `order_id / score / content`）与 `t_wallet_tx.type = 2`（退款流水类型）都是建库时就预留好的加分项位置。评价闭环几乎是免费的，真正的工作量在工单状态机与退款幂等。

建议 **L4** 认领（用户端评价与申诉入口）或 **L3**（管理端客服工作台）。

## 3 业务流程

### 3.1 订单评价

1. 用户在自己的 `PAID` 订单详情中提交 1～5 星、固定标签和可选文字。
2. 服务端从会话身份确定用户，校验订单归属、状态和“一单一条有效评价”约束。
3. 评价发布后，服务端更新或失效重算站点评分摘要；站点详情只返回公开评价，不暴露手机号等个人信息。
4. 管理员可因违规内容隐藏评价，但不能物理删除评价或修改用户原文；隐藏操作必须写审计记录。

### 3.2 客服工单

1. 用户从订单详情选择固定问题类型，填写标题与正文，提交关联该订单的工单。
2. 服务端校验订单归属，创建工单、首条消息和首个事件。用户只可查看自己的工单。
3. 客服在管理端接单，进入处理状态；后续每次回复、状态迁移、负责人变化都写入时间线。
4. 客服需要补充资料时将工单置为 `WAITING_USER`；用户补充文字后自动回到 `PROCESSING`。
5. 客服给出处理结果后置为 `RESOLVED`，用户确认后进入 `CLOSED`。首版不做无限次重开；如仍有争议，用户新建关联工单。

### 3.3 模拟退款

1. 只有关联 `PAID` 订单的费用申诉可以申请退款。客服提交建议退款金额和原因，但无退款权限的角色不能执行资金变更。
2. 具备权限的管理员审批。服务端重新计算可退上限：`订单实付金额 - 已成功退款总额`。
3. 退款执行时在一个事务内写退款记录、增加用户钱包余额、写钱包流水、更新累计退款额、工单事件和审计日志。
4. 执行成功后订单仍保持 `PAID`；退款结果由独立退款记录表达。部分退款后可再次申请，但成功退款累计值不得超过用户实付金额。
5. 首版不返还优惠券，且应在用户界面明确显示“退款进入模拟钱包”。

## 4 状态、金额与不可破坏约束

### 4.1 状态定义

- 核心订单状态仍只使用 `RESERVED`、`CHARGING`、`PENDING_PAYMENT`、`PAID`、`CANCELLED`。退款后订单仍为 `PAID`，不得新增 `REFUNDED`、`AFTER_SALES` 等不兼容状态。
- 评价状态：`PUBLISHED -> HIDDEN`。若现有 UI 需要保存草稿，可增加模块内部 `DRAFT -> PUBLISHED`，但不得让草稿进入评分统计。
- 工单主路径：`SUBMITTED -> ACCEPTED -> PROCESSING -> RESOLVED -> CLOSED`。
- 工单分支：`SUBMITTED -> CANCELLED`；`PROCESSING -> WAITING_USER -> PROCESSING`。首版只允许用户在尚未受理时取消，关闭后不可修改。
- 退款状态：`REQUESTED -> APPROVED -> EXECUTED`，或进入 `REJECTED`、`FAILED`。对 `FAILED` 的重试必须复用同一退款请求和幂等键，不得新建一笔潜在重复退款。

所有状态迁移集中在服务层校验，Socket handler、Qt 页面和 SQL 触发器不得各自维护不同版本的迁移规则。

### 4.2 金额规则

- 订单实付、申请退款、成功退款累计、钱包余额与流水统一使用 64 位整数分，字段建议以 `_cents` 结尾。
- 禁止使用 `float` 或 `double` 计算可退金额，禁止客户端提交“剩余可退金额”作为可信值。
- 必须满足：`0 < 本次退款金额 <= 订单实付金额 - 已成功退款金额`，且钱包加款金额与退款流水金额完全相等。

### 4.3 不可破坏约束

- 用户只能评价、申诉和读取自己的订单与工单；管理员操作必须经过服务端权限校验，不能信任 UI 隐藏按钮。
- 一个订单最多一条有效评价；并发提交依赖数据库唯一约束兜底。
- 工单消息不可覆盖或物理删除，所有状态变更都形成追加式事件。
- 退款只能复用钱包服务，客服模块不得直接执行无流水的余额更新。
- 退款事务任何一步失败都要整体回滚；重复点击、超时重试或并发审批不得重复到账。
- 评价聚合、通知和统计失败可以延迟重算，但不得回滚已经合法完成的退款；它们应与资金主事务解耦或采用可靠的事务后处理。
- 用户输入在 Qt 富文本和 Web 页面显示前必须按上下文转义；服务端限制长度、枚举和分页大小。
- 客服模块不可改变电桩状态，也不可绕过“未结算订单阻止新充电”的核心规则。

## 5 建议架构、数据、协议与 UI

### 5.0 技术路线校准（对齐真实仓库）

| 原文档设计 | **校准后落地** | 为什么 |
| --- | --- | --- |
| `review` 表 | **复用已冻结的 `t_station_review`**（`review_id, station_id, user_id, order_id, score 1..5, content, create_time`） | 建库时就为加分项预留的位置，字段刚好够用 |
| `review` 的 `status`（隐藏）与标签关联 | 冻结表没有这两列。**新建 `t_review_ext`**（`review_id UNIQUE, hidden, hide_reason, tags, version`）旁挂，**不改 `t_station_review`** | 给冻结表加列要走 CR 且波及大屏取数；旁挂零风险 |
| `station_rating_summary` 表 | **不建表。** 评分从 `t_station_review` 实时聚合（`AVG(score)`、`COUNT(*)`，排除 `t_review_ext.hidden = 1`） | 六个站点、演示量级的数据，实时聚合毫秒级；摘要表必然出现与原始评价不一致 |
| `payment_refund` + `refund_request` 两张表 | 合成一张 **`t_refund_req`**（`ticket_id, order_id, apply_fen, status, reason, approver, tx_id, req_id UNIQUE, create_time, done_time`） | MVP 一笔申请对应一次执行，拆两张表只增加事务复杂度 |
| 退款写钱包 | **复用 `t_wallet_tx` 的 `type = 2 退款`**（schema 已定义），并按 `wallet_service.cpp` 的写法用 `BEGIN IMMEDIATE` 更新 `t_user.balance` 与写流水 | 第二套资金账本会让 2301 营收与钱包对不上账 |
| `notification` 表 | **不建表。** MVP 用工单列表的「有新回复」标记（查询时比较 `t_ticket.update_time` 与用户上次查看时间） | 通知系统是独立模块的体量，不在本模块范围 |
| 「订单可评价」判定 | `t_order.status = 3`（已结算）且 `user_id` 匹配且 `t_station_review` 中该 `order_id` 尚无评价 | `order_id` 在冻结表里可空，本模块要求必填并在 `t_review_ext` 上建 `UNIQUE(review_id)`、在查询层保证一单一评 |
| 金额与时间 | 退款金额 `qint64` 整数分，**不得超过 `t_order.amount`**；时间 TEXT 本地时间 | 见 00 第 4.5 节 |
| 新增「订单状态冲突 / 权限不足」错误码 | **复用 `ERR_ORDER_STATUS(4003)` / `ERR_NO_PERMISSION(1004)` / `ERR_BALANCE_NOT_ENOUGH(2004)`** | 见 00 第 4.3 节 |

**退款不改订单状态**：退款后订单**仍为已结算(3)**，退款事实只体现在 `t_refund_req` 与 `t_wallet_tx`。

### 5.1 服务端架构

根据仓库现有分层映射以下职责，不要求创建同名文件：

- `ReviewService`：评价资格、订单归属、唯一性、隐藏及评分聚合触发。
- `TicketService`：工单创建、分派、状态机、消息与事件时间线。
- `RefundService`：审批权限、可退上限、钱包退款、幂等和事务协调。
- `RatingAggregationService`：从公开评价生成站点评分摘要，并提供重算能力。
- `SupportQueryService`：分页、筛选、脱敏及大屏统计，避免 UI 直接读表。

建议调用链：`Qt/Web -> Socket 网关 -> 鉴权/权限 -> 业务服务 -> Repository -> SQLite`。通知可以在主事务成功后创建站内消息；通知发送失败不应造成二次退款。

### 5.2 数据模型

适配现有命名和迁移机制后，至少需要：

| 建议实体 | 关键字段或约束 |
| --- | --- |
| `review` | 订单、用户、站点、星级、正文、状态、创建时间；`order_id` 有效评价唯一 |
| `review_tag` / 关联表 | 固定标签及评价多对多关系；首版标签由管理员预置 |
| `station_rating_summary` | 站点、评价数、星级总和/平均值、更新时间；必须可从原始评价重算 |
| `support_ticket` | 用户、订单、类型、标题、状态、负责人、版本号、创建/更新时间 |
| `ticket_message` | 工单、发送者类型/ID、正文、创建时间；追加写入 |
| `ticket_event` | 工单、事件类型、前后状态、操作者、原因、创建时间；追加写入 |
| `refund_request` | 工单、订单、申请金额分、状态、原因、审批人、幂等键；幂等键唯一 |
| `payment_refund` | 退款请求、订单、成功金额分、钱包流水 ID、执行时间；退款请求唯一 |
| `notification` | 收件用户、类型、关联对象、已读状态；若仓库已有通知表则直接复用 |

`support_ticket.version` 用于乐观锁；状态更新使用“ID + 期望版本 + 期望状态”的条件更新。评价正文、工单正文和回复均设置明确长度上限，索引至少覆盖用户工单列表、管理员状态筛选、订单退款汇总和站点评价查询。

### 5.3 Socket 协议

动作名需适配仓库现有消息 envelope 和命名规范，至少覆盖这些逻辑语义：

| 方向 | 逻辑动作 | 核心输入/输出 |
| --- | --- | --- |
| 用户端 | 创建/查询评价 | 订单、星级、标签、正文；或站点与分页条件 |
| 用户端 | 创建/查询工单 | 订单、问题类型、标题、正文；返回脱敏工单摘要与时间线 |
| 用户端 | 补充消息/确认关闭 | 工单、正文或 `expectedVersion`；返回新状态和版本 |
| 管理端 | 工单列表/详情 | 状态、类型、负责人、时间、分页；返回工单、消息和事件 |
| 管理端 | 接单/回复/迁移状态 | 工单、目标状态、`expectedVersion`、内容或原因 |
| 有权限管理端 | 审批/执行退款 | 退款请求、金额分、原因、`idempotencyKey`；返回退款与钱包流水结果 |
| 管理端 | 隐藏评价 | 评价、原因、`expectedVersion`；返回审计关联信息 |

服务端从会话身份推导用户和管理员权限，不接受请求方任意指定 `userId`、`operatorRole` 或退款到账钱包。列表统一分页并设置最大页大小。至少区分订单不可评价、重复评价、工单归属错误、非法状态迁移、版本冲突、退款无权限、金额超限、重复退款和暂时失败等错误。

### 5.4 UI 范围

- 用户端：`PAID` 订单显示“评价”和“申请售后”；评价表单包含星级、固定标签和文字；工单详情展示状态、消息、事件、退款金额和确认关闭入口。
- 站点详情：显示平均分、评价数和近期公开评价；隐藏评价不得出现。
- 管理端：工单池、状态/类型/负责人筛选、详情时间线、接单、回复、等待用户、解决；具备权限时显示退款审批/执行；评价列表支持带原因隐藏。
- Web 大屏为次要交付，可在已有统计框架中增加未处理工单、平均首次响应时间、平均解决时间、评分和退款趋势；不得展示手机号、私密消息正文或原始敏感信息。
- 没有实时推送能力时使用显式刷新或合理轮询，不为 MVP 引入新的即时通信栈。

## 6 顺序实施步骤

必须按以下顺序实施，每步都给出可检查的产出和验证；发现现有等价能力时优先复用。

### 步骤 1：仓库审计与权限边界确认

- 产出：订单归属和 `PAID` 判定位置、钱包加款/流水事务入口、管理员角色能力、审计方式、拟改文件清单和迁移草案。
- 验证：明确谁能隐藏评价、接单、审批退款和执行退款；运行现有订单与钱包回归测试作为基线。

### 步骤 2：评价闭环

- 产出：评价/标签/评分摘要迁移，评价服务与查询协议，用户评价表单、站点评价列表和管理端隐藏操作。
- 验证：只有订单本人能评价 `PAID` 订单；并发重复评价只有一条成功；隐藏后聚合正确且原文仍保留；恶意文本显示时不执行脚本或富文本。

### 步骤 3：工单与时间线

- 产出：工单、消息、事件数据结构，集中状态机，创建/列表/详情/补充消息协议及用户 UI。
- 验证：归属隔离、分页、非法迁移、取消边界、`WAITING_USER` 往返和追加式时间线测试通过。

### 步骤 4：管理端客服处理

- 产出：工单池、筛选、接单、负责人、回复、解决和乐观锁冲突提示；必要的 RBAC 和审计接入。
- 验证：两名客服并发接单只有一个成功；无权限用户不能读取或修改工单；版本冲突不会覆盖另一人的回复或状态。

### 步骤 5：模拟退款

- 产出：退款申请/审批/执行模型，可退上限计算，钱包加款与流水，幂等退款事务，用户退款结果展示。
- 验证：全额、部分、累计超限、并发执行、重复幂等键、余额写入中途故障和无权限执行测试通过；订单始终保持 `PAID`。

### 步骤 6：通知和基础指标

- 产出：工单回复、状态改变和退款到账的站内通知；评分、响应时间、解决时间和退款额统计接口，已有大屏存在时再接入 UI。
- 验证：通知失败不影响工单或退款主结果；统计可从原始数据重算且不返回用户私密内容。

### 步骤 7：回归、演示与交付说明

## 8 Definition of Done

- [ ] 用户只能对自己的 `PAID` 订单提交一次有效评价，并可在站点查看公开评价与正确评分。
- [ ] 管理员隐藏评价需要权限、原因和审计，原始内容不被物理删除。
- [ ] 工单、消息和事件形成可追溯时间线，所有状态迁移由服务端统一校验。
- [ ] 用户与管理员列表均分页，用户数据按归属隔离，管理操作按角色授权。
- [ ] 全额和部分模拟退款能原子进入用户钱包并生成流水，累计退款不超过实付金额。
- [ ] 重复或并发退款不会二次到账；失败不留下半条流水、半次余额更新或错误状态。
- [ ] 退款后核心订单仍为 `PAID`，没有新增不兼容订单状态，原订单与钱包流程不受影响。
- [ ] 所有金额使用整数分，所有输入有长度、枚举、范围和转义校验。
- [ ] 用户端和管理端只经服务端协议访问业务数据，不直接操作 SQLite。
- [ ] 自动化测试、扩展建表脚本、演示数据和端到端演示步骤可重复运行，交付报告完整列出测试结果与限制。

## 9 风险与降级

| 风险 | 首选处理 | 无法按期完成时的降级 |
| --- | --- | --- |
| 角色系统不完整 | 增加最小客服/退款权限并接入现有审计 | 仅超级管理员可执行退款，但接单与退款均必须审计 |
| 钱包仅支持扣款 | 在钱包服务内增加带业务类型的原子加款接口 | 先完成工单，退款功能隐藏且明确列为未交付，禁止直接改余额 |
| 实时更新工期高 | 复用已有通知或推送 | 用户手动刷新，管理端短轮询；不引入新通信框架 |
| 评分摘要一致性 | 事务后可靠更新并支持重算 | 查询时从公开评价聚合，数据量可控后再缓存 |
| 工单功能膨胀 | 固定问题类型和单负责人 | 不做附件、抄送、转派链、自动 SLA 和无限重开 |
| 大屏开发不足 | 提供统一统计接口 | 延后大屏图表，不影响评价—工单—退款主闭环 |

任何降级都不能牺牲订单归属校验、服务端权限、退款金额上限、整数金额、钱包流水、事务回滚、幂等或核心订单状态兼容。
