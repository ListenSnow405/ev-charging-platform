# 03 · 设备告警与运维工单

## 1 文档用途

本文是扩展模块 03 的任务规格。技术底座、命令字分段、单位口径、接缝规则见 [00-扩展功能模块实施路径推荐.md](00-扩展功能模块实施路径推荐.md) 第 4、5 节；**凡本文第 5 节与 00 第 4 节冲突，以 00 为准**。

本模块把 02 产出的设备事实（连接世代、心跳、遥测、故障上报）变成**可运营的告警与工单闭环**，并复用 `[说明书]` 1.4 明文的远程重启（2112）作为处置手段。管理端页面重、异常路径多，建议 **L3** 认领——他同时是集成主责，告警与工单正好接在联调动线上。

## 3 业务流程

### 3.1 设备异常到唯一活动告警

1. 设备上报心跳、状态或遥测，服务端先完成消息幂等和最新运行事实更新。
2. `HeartbeatMonitor` 定时检测心跳超时；规则引擎判断主动故障、过温和充电异常中断。
3. 首次满足规则时创建 `OPEN` 告警；相同“电桩 + 规则编码”已经存在活动告警时，只更新最近发生时间、次数和最新观测值。
4. 严重故障或离线事件通过项目已有的统一电桩状态入口反映为 `FAULT` 或 `OFFLINE`，不得由告警表直接改电桩状态字段。
5. 服务端向管理端推送增量事件；若项目无稳定推送能力，管理端按更新时间游标增量轮询。

### 3.2 告警确认与工单处理

1. 有权限的管理员确认告警，状态由 `OPEN` 进入 `ACKNOWLEDGED`。
2. 管理员从告警创建工单，或由严重告警按配置自动创建一张工单。
3. 工单依次执行派单、开始处理、记录处理措施、解决和关闭。
4. 每次工单状态变化都写入不可变事件记录；并发修改通过版本号或条件更新避免覆盖。
5. 告警、工单及管理员敏感操作写入审计；没有权限时服务端拒绝请求且不改变状态。

### 3.3 远程重启与结果回传

1. 运维人员在工单或设备详情中发起重启，服务端生成唯一 `commandId`。
2. 命令通过已有设备通信入口发送，并进入等待应答状态。
3. 设备返回成功或失败结果；超过截止时间仍无结果则标记超时。
4. 同一个 `commandId` 的重复应答只处理一次，并写入命令时间线和工单事件。
5. 重启成功不等于故障已恢复，规则引擎仍需根据后续心跳和遥测判断恢复条件。

### 3.4 自动恢复与关闭

1. 规则恢复条件连续满足后，活动告警进入 `RESOLVED`。
2. 电桩最终状态必须由统一状态协调逻辑结合最新设备事实和活动订单重新计算，不能无条件写回 `IDLE`。
3. 运维人员确认处理结果后关闭工单；确认告警信息完整后将告警关闭。
4. 同一故障在旧告警关闭后再次发生，应创建新的告警实例，保留完整历史。

## 4 状态与不可破坏约束

### 4.1 告警状态

正常迁移为：

`OPEN -> ACKNOWLEDGED -> RESOLVED -> CLOSED`

允许无人确认但故障已自行恢复时执行 `OPEN -> RESOLVED`。`CLOSED` 为终态，不回退；同一规则再次触发时创建新告警。

### 4.2 工单状态

正常迁移为：

`OPEN -> ASSIGNED -> PROCESSING -> RESOLVED -> CLOSED`

`OPEN` 或 `ASSIGNED` 且尚未实际处理时可进入 `CANCELLED`。`RESOLVED` 可在验收不通过时退回 `PROCESSING`，但必须填写原因并产生事件。`CLOSED / CANCELLED` 为终态。

### 4.3 命令状态

若已有设备命令状态则直接复用。缺失时，MVP 可采用：

`PENDING -> SENT -> SUCCEEDED / FAILED / TIMED_OUT / CANCELLED`

### 4.4 不可破坏约束

1. 对同一“电桩 + 规则编码”同时最多存在一条活动告警，重复异常只能累计，不能形成告警风暴。
2. 告警恢复不会自动关闭工单；工单关闭也不能伪造设备恢复事实。
3. 告警引擎不能直接把电桩恢复为 `IDLE`。有活动订单时必须遵循原订单/电桩状态协调规则。
4. 不得修改电桩状态。**只有在用(0)/闲置(1)/故障(2) 三态**（`[说明书]` 1.4 明文），离线走 `t_pile.online`，不得增加近义状态；详见 [00 第 4.5.1 节状态命名映射](00-扩展功能模块实施路径推荐.md)。
5. 不得由本模块擅自修改订单状态 `RESERVED / CHARGING / PENDING_PAYMENT / PAID / CANCELLED`。充电中断如何进入待结算或异常处置，应调用已有订单服务并服从其规则。
6. 预约和开始充电仍由原业务服务在事务内复核设备可用性，管理端显示“恢复”不能绕过该检查。
7. 设备消息、规则触发、命令应答都必须幂等；服务重启不能产生重复告警或永久等待命令。
8. 告警状态、工单状态、事件记录和对应审计应在同一事务边界内保持一致。
9. 时间判断使用服务端统一时钟；数据库保存统一时区或 UTC，界面再按本地时区展示。

## 5 建议架构、数据、协议与 UI

### 5.0 技术路线校准（对齐真实仓库）

### 5.1 服务端组件

- `DeviceRuntimeStateRepository`：保存每个设备的最新心跳、状态和必要遥测摘要。
- `HeartbeatMonitor`：按固定周期扫描心跳超时并产生离线观测。
- `AlertRuleEngine`：执行阈值、持续时长、去重和恢复判断。
- `AlertService`：告警查询、确认、解决与关闭。
- `WorkOrderService`：创建、派单、处理、解决、退回、关闭和事件记录。
- `DeviceCommandService`：重启命令创建、发送、应答、超时和查询；优先复用数字孪生模块已有实现。
- `OperationEventPublisher`：管理端增量通知；没有事件总线时可退化为带游标轮询。

规则判断与 Socket 解析分离，工单状态迁移与 UI 分离。不要让界面直接更新数据库状态。

### 5.2 建议数据

- `device_runtime_state`：电桩编号、最后心跳、最近序号、在线标志、温度、功率、设备状态、更新时间。
- `alert_rule`：规则编码、告警级别、阈值、持续时间、恢复条件、启用状态。
- `device_alert`：电桩、规则、级别、状态、首次/最近发生时间、累计次数、最新观测、确认人和解决时间。
- `maintenance_work_order`：工单号、关联告警、电桩、负责人、优先级、状态、处理摘要、版本号和时间。
- `work_order_event`：工单、事件类型、前后状态、操作者、备注、`requestId` 和时间，只新增不覆盖。
- `device_command`：若已有则复用；至少需要 `commandId`、设备、类型、状态、请求/截止/应答时间和结果。

活动告警唯一性优先用数据库部分唯一索引或等价活动键保证；工单编号、`commandId`、消息序号/消息编号应唯一。为设备与更新时间、告警状态与级别、工单状态与负责人建立查询索引。扩展建表脚本必须幂等，可重复执行。

### 5.3 首期规则

| 规则 | 触发条件 | 恢复条件 | 建议级别 |
| --- | --- | --- | --- |
| 离线 | 最后心跳超过可配置阈值 | 连续收到有效心跳，并通过最短稳定时间 | 严重 |
| 主动故障 | 设备上报明确故障码 | 设备上报故障清除且运行事实正常 | 严重或警告 |
| 过温 | 温度连续超过阈值一段时间 | 温度连续低于恢复阈值一段时间，使用回差避免抖动 | 严重 |
| 充电异常中断 | 充电过程中设备报告非正常停止或连接中断 | 该次异常事实已由充电业务确认处理 | 警告 |

阈值先采用初始化配置，不需要首版开发通用规则编辑器。

### 5.4 建议协议动作

设备侧优先复用数字孪生模块动作，例如心跳、遥测、故障报告和命令应答；不要为同一消息再定义一套协议。管理侧建议动作：

- `ALERT_LIST`、`ALERT_DETAIL`、`ALERT_ACKNOWLEDGE`、`ALERT_CLOSE`。
- `WORK_ORDER_LIST`、`WORK_ORDER_CREATE`、`WORK_ORDER_ASSIGN`、`WORK_ORDER_START`、`WORK_ORDER_RESOLVE`、`WORK_ORDER_REOPEN`、`WORK_ORDER_CLOSE`、`WORK_ORDER_CANCEL`。
- `DEVICE_RESTART_REQUEST`、`DEVICE_COMMAND_QUERY`。
- `MAINTENANCE_METRICS_QUERY`、`OPERATION_EVENT_POLL`（仅在没有推送时使用）。

沿用统一消息格式、认证、`requestId`、错误码和分页结构。建议增加 `INVALID_STATE_TRANSITION`、`ACTIVE_ALERT_EXISTS`、`WORK_ORDER_VERSION_CONFLICT`、`DEVICE_COMMAND_TIMEOUT` 和 `DEVICE_UNAVAILABLE` 等稳定错误码。

### 5.5 管理端与 Web UI

- 告警中心：级别、站点、设备、规则、状态和时间筛选，支持确认和查看时间线。
- 工单池：待处理、我的工单、处理中、待关闭和历史工单，显示负责人、版本和处理备注。
- 电桩详情：最新心跳、必要遥测、活动告警、关联工单和命令时间线。
- 运维总览：活动告警数、严重级别分布、在线率、平均首次响应时间、平均修复时间。
- 用户端：仅展示“故障/离线/暂不可用”等用户可理解信息，不暴露故障码和运维备注。

统计必须从告警、工单事件和设备事实聚合；页面中不得散落硬编码数字。

## 6 按顺序实施步骤

### 步骤 0：仓库勘察与依赖确认

**产出：** 定位服务端、设备消息入口、统一电桩状态更新入口、订单服务、扩展建表脚本、管理端、权限审计和测试命令；列出现有消息字段与状态写入点，给出不超过 8 条的短计划。

**验证：** 能用现有方式产生至少一条心跳和一条故障事件；若核心源码或设备事件入口缺失，报告缺口，不在本任务中实现完整数字孪生模块。

### 步骤 1：数据结构与状态迁移

**产出：** 增加最新运行事实、规则、告警、工单、工单事件所需数据结构，按需复用/补齐设备命令表；集中定义合法状态迁移。

**验证：** 空库和已有库迁移成功；重复执行不重复建表或种子；非法状态值受服务层和约束保护。

### 步骤 2：设备事实与消息幂等

**产出：** 将既有心跳、遥测、故障消息转换为统一内部观测；按消息编号或递增序号去重；更新每台设备最新事实。

**验证：** 重复、乱序和延迟消息不会覆盖更新事实或重复触发业务；关键日志可通过设备号和消息编号追踪。

### 步骤 3：基础规则与告警去重

**产出：** 实现离线、主动故障、过温和异常中断规则；支持持续时间、回差、活动告警唯一性和累计次数。

**验证：** 同一异常重复上报只得到一条活动告警；阈值附近抖动不反复开关告警；不同规则可各自产生告警。

### 步骤 4：告警生命周期与恢复协调

**产出：** 确认、自动解决、人工关闭及事件/审计记录；通过统一状态入口反映 `FAULT/OFFLINE`，恢复时调用状态协调逻辑。

**验证：** 非法迁移被拒绝；故障恢复时，有活动预约/充电的电桩不会被错误写成 `IDLE`；本模块不直接改变订单状态。

### 步骤 5：工单闭环

**产出：** 从告警创建工单、派单、开始、解决、退回、关闭和取消；每次变化写事件；用版本号或条件更新处理并发。

**验证：** 完整状态流可运行；两名管理员同时操作时只有一个条件更新成功；历史事件按时间完整展示。

### 步骤 6：远程重启集成

**产出：** 在已有设备命令服务上接入重启请求、唯一 `commandId`、应答和超时；将结果关联到工单时间线。

**验证：** 成功、失败、超时、重复应答分别得到唯一稳定结果；重启成功不会直接把告警或工单错误关闭。

### 步骤 7：管理端页面与基础指标

**产出：** 告警列表/详情、工单池/详情、设备命令时间线和最小运维指标；复用现有 Qt 模型、网络封装和 UI 风格。

**验证：** 筛选、分页、空状态、错误提示和权限控制可用；增量推送或游标轮询不会产生重复行；统计值可用数据库查询复核。

### 步骤 8：恢复、回归与演示

**产出：** 启动恢复逻辑，处理过期命令、活动告警和未关闭工单；补充自动化测试、演示种子和运行说明。

**验证：** 在告警、命令和工单处理中重启服务，重启后无重复告警、无永久等待命令、工单历史不丢失；预约故障设备仍被原服务拒绝。

## 7 测试矩阵

| 类型 | 场景 | 预期结果 |
| --- | --- | --- |
| 离线 | 设备停止心跳超过阈值 | 只产生一条活动离线告警，设备经统一入口反映不可用 |
| 去重 | 同一故障重复上报 100 次 | 活动告警仍为一条，次数和最近时间正确 |
| 过温 | 温度短暂越界后恢复 | 未达到持续时间时不触发；达到后触发，恢复遵循回差和稳定时间 |
| 多规则 | 同一设备同时离线和过温 | 各规则独立记录，不互相覆盖 |
| 恢复 | 有活动预约或充电时设备重新上线 | 告警可解决，但电桩不被无条件写成 `IDLE`，订单状态不被本模块修改 |
| 工单 | 创建、派单、处理、解决、关闭 | 状态正确，每一步都有事件和审计 |
| 非法迁移 | `OPEN` 工单直接关闭或终态回退 | 返回 `INVALID_STATE_TRANSITION`，数据不变 |
| 并发 | 两名管理员同时处理同一工单 | 只有一个版本更新成功，另一方得到冲突响应 |
| 权限 | 无权限账号确认告警或重启设备 | 服务端拒绝，无状态变化，产生越权审计 |
| 命令 | 重启成功、失败和无应答 | 分别进入正确终态，重复应答不重复生效 |
| 重启恢复 | 服务在活动告警和待应答命令期间重启 | 状态可恢复，过期命令最终超时，不产生重复告警 |
| 回归 | 预约故障/离线电桩 | 原预约服务拒绝；恢复后的可用性仍由原规则判定 |
| 统计 | 计算在线率、响应和修复时间 | 与事实表及事件时间人工查询一致，界面无硬编码值 |

## 8 Definition of Done

- [ ] 四条首期规则可由真实或现有模拟设备事件触发，规则阈值集中配置。
- [ ] 活动告警具备数据库级或等价唯一保护，重复消息不会制造告警风暴。
- [ ] 告警确认、解决、关闭和工单完整状态流均经过服务端合法迁移检查。
- [ ] 工单事件不可变且可追踪，状态写入具备事务与并发保护。
- [ ] 远程重启具有唯一命令号、成功/失败/超时结果和幂等应答。
- [ ] 故障恢复不会无条件写 `IDLE`，不会由本模块擅自改变订单状态。
- [ ] 管理端可查询、筛选和处理告警/工单，并查看设备命令时间线。
- [ ] 基础运维指标来自统一数据源，可通过查询复核，不使用页面硬编码。
- [ ] 服务重启恢复、无权限、非法迁移、并发操作和故障设备预约测试通过。
- [ ] 相关工程构建成功，测试与演示步骤可重复执行。
- [ ] 最终报告列明实际修改文件、协议/数据库变化、验证结果和未实现项。

## 9 风险与降级

| 风险 | 优先处理 | 可接受降级 |
| --- | --- | --- |
| 设备事件入口尚不稳定 | 先建立薄适配层，把既有消息转换为内部观测 | 用测试夹具或管理端仅限开发环境的故障注入验证规则；不得顺带开发完整数字孪生模块 |
| 告警风暴 | 活动告警唯一约束、持续时间、回差和累计更新 | 首期只启用离线、主动故障和过温三条规则，异常中断延后 |
| 高频遥测导致 SQLite 膨胀 | 只保留最新事实、状态变化和固定间隔采样 | MVP 不保存原始全量遥测，但告警触发快照必须保留 |
| 实时推送不可靠 | 使用现有推送通道并保留断线恢复 | 管理端按 `updatedAt + id` 游标增量轮询 |
| 自动恢复误判 | 使用恢复阈值、稳定时间和最新消息序号 | 告警只自动进入 `RESOLVED`，由管理员确认后 `CLOSED` |
| 多人并发覆盖 | 版本号或条件更新加事务 | 按工单串行处理；数据库约束仍作为最终防线 |
| 状态协调边界不清 | 只调用现有电桩/订单服务，不直接改核心表 | 暂不自动变更电桩状态，只标记告警并阻止通过现有可用性校验 |

降级不得取消告警去重、工单状态校验、命令幂等和核心订单/电桩状态保护。
