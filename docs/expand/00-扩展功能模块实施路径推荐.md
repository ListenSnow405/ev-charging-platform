### 4.2 报文与命令字：不动信封

**信封已冻结，扩展一律不改。** 请求 `{cmd,seq,token,data}`，响应 `{cmd,seq,code,msg,data}`，推送 `seq=0,code=0`。

01–10 文档中出现的 `version` / `messageType` / `action` / `requestId` / `timestamp` / `connectionGeneration` **一律不加入信封**：
- **动作名 → 数字命令字**：文档里的 `ADMIN_LOGIN`、`QUEUE_JOIN`、`ALERT_LIST` 等只是逻辑名，落地时映射为下表段内的数字。
- **`requestId` / `idempotencyKey` → 放进 `data`**，字段名统一 `reqId`（string，客户端生成，长度 ≤ 64），见 4.6。
- **`version` → 不需要**：全组同仓库同版本发布，加版本号只会多一条无人维护的分支。
- **设备消息**（02/10）沿用 9000 段与同一信封，`pileCode` 放 `data`，**不要另立一套设备协议**。

### 4.4 数据库：没有迁移框架，用 ext 脚本

现实：`docs/db-schema.sql` **每张表都以 `DROP TABLE IF EXISTS` 开头**，重跑即清库；仓库没有 `schema_migration` 机制。01–10 中所有「可重复执行的迁移」表述按下述落地：

1. 每个模块新增 **一个** 文件：`docs/db-schema-ext-NN.sql`（NN = 模块号），属主 = 认领人，L2 复核。
2. 文件内**只允许** `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` / `INSERT OR IGNORE`。**禁止 `DROP`，禁止改动 `docs/db-schema.sql` 已有表**。
3. 必须**幂等**：重复执行不报错、不产生重复种子数据。
4. `scripts/build-all.sh` 建库后按编号顺序执行全部 `docs/db-schema-ext-*.sql`（B3，L3 落地）。
5. 确实需要给既有表加列 → **走 CR**，由 L2 在 `db-schema.sql` 加列，同时在 ext 脚本里补一条幂等的 `ALTER TABLE ADD COLUMN`（SQLite 不支持 `IF NOT EXISTS`，用先查 `PRAGMA table_info` 再决定的方式，或由 L2 统一处理）。
6. 外键指向核心表可以，**核心表不得反向依赖扩展表**——功能开关关掉时核心必须仍能建库、仍能跑。

### 4.5 单位与时间口径（**勘误表**）

01–10 沿用了一套与本项目不同的口径。**下表右列为准**，左列一律不要用：

| 项 | 文档原写法 | 本项目口径（以此为准） | 为什么 |
| --- | --- | --- | --- |
| 时间 | UTC / ISO 8601 带时区 | `TEXT 'yyyy-MM-dd HH:mm:ss'` **本地时间** | `db-schema.sql` 已冻结此格式；近 7/30 日趋势用 `date()` 直接聚合，两套时间必然对不上账 |
| 金额 | 整数最小货币单位 / 微元每千瓦时 | `qint64` **整数分** | CLAUDE.md 硬性规则 3 |
| 单价 | 微元/千瓦时 | **分/度**（`INTEGER`，同 `t_station.price`） | 分时计价 152 分/度这一精度足够；引入第二种单价单位是纯风险 |
| 电量 | Wh 整数 | **`kwh_x100`（度 × 100 的整数）** | `t_order.kwh_x100` 已冻结；Wh 与 kwh_x100 混用必然出错 |
| 功率 | W 整数 | **kW（`REAL`）** | `t_pile.power`、`t_load_forecast.load_kw` 均为 REAL kW；功率是物理量不受金额规则约束 |
| SOC / 百分比 | 基点 0..10000 | **整数百分比 0..100** | 本项目无需万分之一精度 |
| 碳排放 | mg / mg per kWh | **整数克 g**，因子 `g_per_kwh` 整数 | 因子量级约 581 g/kWh，用克即是整数，无需再放大 1000 倍 |
| 主键 | UUID / 业务编号字符串 | `INTEGER PRIMARY KEY AUTOINCREMENT` + 必要时 `xx_no TEXT UNIQUE` | 与 `t_order(order_id, order_no)` 一致 |

01–10 用的是一套英文逻辑状态名，与仓库里已冻结的枚举不是一一对应。**落地一律用右列**，文档里的英文名只当作阅读别名：

**订单状态** —— 权威定义在 `common/protocol.h` 的 `OrderStatus` 与 `t_order.status`：

| `RESERVED` | `ORDER_RESERVED` | 0 | 已预约 |
| `CHARGING` | `ORDER_CHARGING` | 1 | 充电中 |

**电桩状态** —— `[说明书]` 1.4 明文**只有三种**，权威定义在 `PileStatus` 与 `t_pile.status`：

| 文档写法 | 落地 | 说明 |
| --- | --- | --- |
| `CHARGING` | `PILE_IN_USE = 0` 在用 | |
| `IDLE` | `PILE_IDLE = 1` 闲置 | |

### 4.6 幂等：不动信封，放进 data

写操作幂等按以下方式实现，**不新增 `idempotency_record` 通用表**：

- 需要幂等的扩展命令，其 `data` 携带 `reqId`（客户端生成的唯一串）。
- 该模块的业务表上建 **`UNIQUE(reqId)`** 或等价活动唯一索引；重复请求命中唯一约束时，**读回首次结果原样返回，不报错**。
- 涉及金额的写操作（退款、企业扣款、模拟补偿）必须在事务内完成，事务用 `BEGIN IMMEDIATE`（与 `wallet_service.cpp` 现有做法一致，避免 SQLite 读锁升写锁的丢失更新）。

### 4.7 功能开关：复用 t_sys_config，不新建表

- 键名 `feat_NN_<模块短名>`，值 `0`/`1`，如 `feat_04_queue`。
- 服务端启动时读取；**关闭的模块干脆不注册 handler**，客户端调用即得 `ERR_CMD_UNKNOWN(1005)`——这比返回一个新错误码更省事，也天然满足"关闭后核心闭环无回归"。
- 客户端对应入口按开关隐藏；拿不到开关状态时**按关闭处理**，不显示会报错的按钮。

## 5 五人自选：认领机制

### 5.1 认领规则

1. **认领单位 = 一个模块**，在 [CLAIM.md](CLAIM.md) 登记：模块号、认领人、认领日、当前步骤、阻塞项。不登记不算认领。
2. **每人同时只持一个「进行中」模块。** 第二顶帽子（契约维护 / 评审组织 / 集成构建 / 测试回归 / 配置归档）不变，扩展不是把它替换掉。
3. **先到先得，但依赖优先**：第 3 节里被别人依赖的模块（01/02）优先于叶子模块被认领。
4. **认领可以放弃**，但必须在 CLAIM.md 写明停在哪一步、已合入什么、遗留什么，不留半截无人认领的分支。
5. **两人组队做一个模块是允许的**，按「服务端切片 / 客户端切片」拆，两人各自登记。这对 04、05、09 这类前后端都重的模块更现实。
6. 本职工作（R0 与 W3 联调）**优先级永远高于扩展**。联调周有人卡住时，扩展模块整体让路。

### 5.2 接缝最小化（**并行不打架的关键**）

CLAUDE.md 第 4 节「agent 只能修改自己所属目录」在扩展期会被打破——几乎每个扩展模块都要同时动 `server/biz/` 和某个客户端。解决办法不是放开边界，而是**把接缝压到一行**：

| 位置 | 规则 |
| --- | --- |
| 服务端业务 | **新建独立文件** `server/biz/ext_NN_<模块>_service.cpp`，导出一个 `registerExtNNService()`。**不改他人既有 service 文件** |
| 服务端注册 | 在 `server/main.cpp` 的 `registerAllServices()` **只加一行调用**。这是全模块唯一允许的公共文件改动 |
| 管理端 | 新建 `admin-client/ext_NN_*.{h,cpp}` 一个页面类；在 `main_window.cpp` **只加一行 addTab** |
| 用户端 | 同上，`user-client/ext_NN_*.{h,cpp}` + 一行入口 |
| 数据库 | 只加 `docs/db-schema-ext-NN.sql`，见 4.4 |
| 契约 | 只加 `common/protocol_ext.h` / `common/error_code_ext.h` 自己段内的行，见 4.3 |
| 大屏 / 模型 | `dataviz/` 与 `ml/` 内新增独立文件，不改 `export_snapshot.py` 既有口径（要改走 CR，它已与服务端 2301–2303 对齐过） |

**冲突只会出现在四个文件**：`server/main.cpp`、两个客户端的 `main_window.cpp`、`common/*_ext.h`。每处都只有一行，`git rebase` 时手动解一次即可。

> 如果一个模块无法只加一行接缝就接进去，**停手先提出来**——那说明它在改核心流程（例如 05 要改结算、09 要改预约付款方），这类改动必须由核心属主（L2）评审并同意，不能由认领人直接落。

### 5.3 契约扩展文件

新增两个文件，属主 = **全体扩展认领人共同维护**，L1 每周复核一次合规（段内、无重号、与文档登记一致）：

```
common/protocol_ext.h      扩展命令字，按 4.3 分段，每行注明模块号
common/error_code_ext.h    扩展错误码，按 4.3 分段，errMsgExt() 返回描述
```

它们**不是冻结契约**，但同样只加不改：改动别人段内的行 = 改契约，走 CR。

### 5.4 阻塞与仲裁

| 情况 | 怎么办 |
| --- | --- |
| 需要 B1/B2 但还没做 | 在 CLAIM.md 挂「阻塞 B1」，先做模块内不依赖它的切片（表、只读查询、界面），**不要自己造定时器/推送** |
| 两个模块都想改同一张核心表 | 停手，两人 + L2 一起定，走 CR。先改的人不获得优先权 |
| 模块 A 依赖模块 B 尚未完成的能力 | A 先按接口写死一份桩数据（比照 `mock/` 做法），B 完成后换真实调用。**桩数据全程保留** |
| 扩展模块让核心闭环回归 | 立即关掉功能开关（4.7），回归优先；扩展的价值永远低于核心可演示 |

## 8 质量门禁（每个模块 DoD 之外的通用项）

标记完成需同时满足：

1. `docs/db-schema-ext-NN.sql` 可在**空库和已有库上重复执行**，不报错、不产生重复种子。
2. 客户端只经 Socket 调服务端，**不直接读写 SQLite**（`ml/` 的离线只读除外）。
3. 服务端校验身份、角色、状态与输入边界；越权请求即使绕过界面直接构造报文也被拒。
4. 写操作有事务边界；金额相关走 `BEGIN IMMEDIATE`；重复 `reqId` 不产生第二次副作用。
5. **异常路径有测试**：重复请求、并发请求、断线重连、服务重启后状态一致。agent 生成的正常流程通常没问题，异常路径几乎必漏。
6. 新增统计能与订单 / 设备 / 钱包明细**对账**，页面无硬编码演示数字。
7. `t_sys_config` 开关置 0 后，核心闭环冒烟测试全过。
8. 至少准备**一个正常演示 + 一个异常演示**场景，写进模块文档。
9. 遵守 CLAUDE.md 第 5 节五条硬性规则；`FrameCodec`、`threadDb()`、`qint64` 分、信号槽跨线程、Qt 6.2.4 API 逐条自查。
