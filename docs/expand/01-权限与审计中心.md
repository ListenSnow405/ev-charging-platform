# 01 · 权限与审计中心

## 1 文档用途

本文是扩展模块 01 的任务规格，供**认领人**（个人或两人组队）实施。技术底座、命令字分段、单位口径、接缝规则见 [00-扩展功能模块实施路径推荐.md](00-扩展功能模块实施路径推荐.md) 第 4、5 节，本文不重复；**凡本文第 5 节与 00 第 4 节冲突，以 00 为准**。

本模块只扩展管理端身份、授权与审计。普通用户仍走手机号免密登录（`[说明书]` 1.4），订单与电桩状态一律沿用 `common/protocol.h` 已冻结的枚举，本模块不新增、不重命名。

**本模块是 03 / 05 / 07 / 09 所有管理端写操作的前置。** 若无人认领，由 L2 在开始 05 之前先做掉——校准后只需 2～3 日。

## 3 业务流程

### 3.1 管理员登录与请求鉴权

1. 管理端提交账号、密码和 `requestId`。
2. 服务端检查账号状态和失败次数，使用密码摘要验证密码。
3. 验证成功后创建随机会话令牌，只把令牌明文返回给当前客户端，数据库只保存令牌摘要。
4. 后续每个管理动作携带令牌；服务端解析会话、管理员状态和权限版本。
5. 请求分发到业务服务之前，服务端根据“动作—权限”注册表作授权判断。
6. 允许的请求进入原业务服务；拒绝的请求不触发业务写入。
7. 对登录、退出、越权以及已登记的敏感动作记录审计结果。

客户端隐藏无权限菜单只是交互优化。即使客户端直接构造 Socket 请求，服务端也必须返回 `PERMISSION_DENIED`。

### 3.2 角色分配与权限生效

1. 超级管理员选择目标管理员及一个或多个角色。
2. 服务端确认操作者拥有角色分配权限，并校验“最后一个有效超级管理员”保护规则。
3. 在一个事务中更新角色分配、递增目标管理员的权限版本并写入审计记录。
4. 目标管理员下次请求时发现权限版本变化，服务端重新加载权限；实现更简单时可直接撤销其全部活动会话并要求重新登录。

MVP 不允许普通管理员给自己提权，也不允许冻结、删除或移除最后一个有效超级管理员的超级管理员角色。

### 3.3 敏感操作审计

敏感业务服务调用统一审计接口。至少覆盖：管理员登录、角色分配、用户冻结/解冻、价格发布、退款或余额调整、电桩远程重启、工单状态变化。

审计记录同时保存业务动作是否成功。失败记录只保存必要的失败原因和错误码，不记录密码、完整令牌、地图密钥、设备密钥或大段请求原文。

### 3.4 审计查询

有 `audit.read` 权限的管理员可按时间、操作者、动作、资源类型、对象编号和结果分页查询。服务端负责分页、排序和脱敏，管理端不得一次加载全表。

## 4 状态与不可破坏约束

### 4.1 模块状态

- 管理员：`ACTIVE / FROZEN`。
- 会话：`ACTIVE -> REVOKED` 或 `ACTIVE -> EXPIRED`；终止状态不得恢复为 `ACTIVE`。
- 审计记录：只新增、只查询，不提供普通业务更新或删除接口。

### 4.2 不可破坏约束

1. 服务端授权是唯一可信结果，任何管理接口都不能只依赖界面按钮是否可见。
2. 管理动作未登记所需权限时默认拒绝，不能默认放行；登录、健康检查等匿名动作只能通过集中、显式的公共动作白名单开放。
3. 数据库不得保存管理员明文密码、完整会话令牌或可逆密码密文。
4. 演示账号仍可初始化为 `admin / 123456`，但落库内容必须是带独立随机盐的密码摘要。
5. 冻结管理员后，其活动会话必须立即或至迟在下一次请求时失效。
6. 角色分配、权限版本变化及相应审计记录必须在同一事务中提交。
7. 审计日志失败不得把已提交的高风险业务操作伪装成“无记录成功”；事务内操作应整体回滚，无法同事务覆盖的读操作或登录失败应采用可靠的独立审计写入。
8. 高风险写动作携带 `requestId` 或幂等键，重复请求不得重复退款、重复调整余额或重复下发设备命令。
9. 不得冻结、删除或移除最后一个有效超级管理员的关键角色。
10. 不修改既有订单状态与电桩状态。**电桩只有在用/闲置/故障三态**（`[说明书]` 1.4 明文），离线是独立的 `t_pile.online` 列；详见 [00 第 4.5.1 节状态命名映射](00-扩展功能模块实施路径推荐.md)。

## 5 建议架构、数据、协议与 UI

### 5.0 技术路线校准（对齐真实仓库）

原文档假设仓库里什么都没有。实测有一半已经存在，以下逐条替换原设计：

| 原文档设计 | **校准后落地** | 为什么 |
| --- | --- | --- |
| `admin_session` 表落库令牌摘要 | **不建表。** 复用 `server/net/session.h` 的内存 `SessionTable` | 协议 §6 已冻结：32 位 hex token、TTL 7200s、`validate()` 刷新活跃时间。落库会话是纯范围膨胀，且要动 L1 冻结文件 |
| 冻结管理员后会话失效 | 直接调用**已有的** `SessionTable::invalidateSessions(id, ROLE_ADMIN)` | CR-003 已实现并冻结，用户侧同款机制在跑 |
| PBKDF2-HMAC-SHA256 + 每账号随机盐 | **MVP 保持 `db-schema.sql` 已冻结的 SHA-256**；要改**必须走 CR**（同时改 schema 与种子摘要），CR 未批前不得擅自改 | 与"实训环境不做 TLS"是同一类已知取舍，写进设计文档即可；`admin/123456` 是 `[说明书]` 明文，摘要值写死在冻结的 schema 里 |
| `role` 表 + 改 `Role` 枚举支持五种角色 | **不动 `enum Role { ROLE_USER, ROLE_ADMIN }`**。`SessionInfo.role` 仍是 `ROLE_ADMIN`，五种管理员角色放 `t_perm_role` + `t_perm_admin_role`，**按 `admin_id` 查表** | `session.h` 是 L1 冻结文件；改枚举会波及全部已注册 handler 与两个客户端 |
| `audit_log` 表 | **新建 `t_audit_log`**（ext-01），不动已冻结的 `t_admin_oplog` | `t_admin_oplog` 缺 `result` / `err_code` / `req_id`；给它加列要动 L2 的冻结表。既有写操作继续写 oplog，扩展写操作写 `t_audit_log`，审计页两表 UNION 查询 |
| `login_attempt` 表做登录限流 | **MVP 用进程内 `QHash<account, {失败次数, 首次失败时刻}>` + 读写锁**，重启清零并在文档写明 | 一张只为限流存在的表，成本高于收益；限流不是说明书要求 |
| 新增 `UNAUTHENTICATED` / `SESSION_EXPIRED` / `PERMISSION_DENIED` / `ACCOUNT_FROZEN` 错误码 | **一律复用现有码**：`ERR_NOT_LOGIN(1002)` / `ERR_TOKEN_INVALID(1003)` / `ERR_NO_PERMISSION(1004)` / `ERR_USER_FROZEN(2003)` | 语义重复的错误码会让两个客户端各写一套分支。**只新增下表两个** |
| 在 `Dispatcher` 里加统一鉴权中间件 | **不改 `server/net/dispatcher.cpp`**（L1 冻结）。改为每个扩展 handler 首行调 `requirePerm(req, "xxx")`；核心 2000 段接入需 L2 同意后逐个加一行 | 5.2 接缝规则：公共文件只允许一行改动 |
| 「未登记动作默认拒绝」 | **仅对扩展段（3000+）生效**：`requirePerm` 查不到登记即返回 1004。核心段维持现有 `needAuth` + role 校验不变 | 对已上线的 25 个命令字改判定基线，等于让 L2/L3/L4 的既有功能一起回归 |

**建表脚本 `docs/db-schema-ext-01.sql`**（全部 `CREATE TABLE IF NOT EXISTS`，禁止 DROP）：

`t_perm_role`（角色码/名称/内置标志）、`t_perm_perm`（权限码/资源/动作）、`t_perm_role_perm`（`UNIQUE(role_code, perm_code)`）、`t_perm_admin_role`（`UNIQUE(admin_id, role_code)`）、`t_audit_log`（`admin_id, action, target, detail, result, err_code, req_id, create_time`，`UNIQUE(req_id)` 保证幂等，索引覆盖 `create_time` / `admin_id` / `action`）。种子用 `INSERT OR IGNORE` 写入五种角色、权限集合，并把 `admin` 绑为超级管理员。

**时间与金额**：`create_time` 一律 `TEXT 'yyyy-MM-dd HH:mm:ss'` 本地时间（`datetime('now','localtime')`）；本模块不涉及金额。

### 5.1 服务端组件

名称可按现有代码风格调整，但职责必须分开：

- `AdminAuthService`：密码验证、登录失败限制、密码修改。
- `SessionService`：令牌生成、摘要保存、到期、退出和强制失效。
- `AuthorizationMiddleware`：会话解析、管理员状态检查、动作权限检查。
- `RolePermissionService`：内置角色、权限查询和角色分配。
- `AuditService`：构造、脱敏、写入和分页查询审计记录。
- 动作权限注册表：集中维护 Socket 动作及其最低权限；登录、健康检查等匿名动作使用显式公共白名单，避免在 UI 或各业务函数内散落字符串判断。

若项目尚无统一中间件，可在现有 Socket 请求分发器进入业务服务之前增加单一鉴权入口，不要借机重写整个网络层。

### 5.2 建议数据

在复用现有管理员表的前提下补齐字段；不要无依据建立第二套管理员主表。逻辑数据如下：

- `admin_user`：账号、密码摘要、盐、状态、权限版本、创建/更新时间。
- `role`：角色编码、名称、是否内置、状态。
- `permission`：权限编码、资源、动作、说明。
- `admin_role_assignment`：管理员与角色关联，组合唯一。
- `role_permission`：角色与权限关联，组合唯一。
- `admin_session`：令牌摘要、管理员编号、权限版本、到期时间、状态、客户端信息。
- `login_attempt`：账号标识、结果、失败原因、时间；仅保存限流所需信息。
- `audit_log`：操作者、角色快照、动作、资源、对象编号、必要前后值、结果、错误码、`requestId` 和时间。

至少为管理员账号、会话令牌摘要、权限编码建立唯一索引；为审计时间、操作者、动作、资源与结果建立适合分页查询的索引。扩展建表脚本与种子数据必须幂等，可重复执行。

密码算法优先复用仓库中已经正确使用的安全库；若没有，可实现 PBKDF2-HMAC-SHA256，并为每个账号生成独立随机盐和足够迭代次数。不得自行设计加密算法。

### 5.3 建议 Socket 动作

- `ADMIN_LOGIN`、`ADMIN_LOGOUT`、`ADMIN_SESSION_INFO`。
- `ADMIN_LIST`、`ADMIN_STATUS_UPDATE`、`ADMIN_ROLE_ASSIGN`。
- `ROLE_LIST`、`PERMISSION_LIST`。
- `SESSION_REVOKE`、`AUDIT_LOG_QUERY`。

沿用现有消息包格式，不创建第二套协议。每个请求至少保留 `action`、`requestId`、认证信息和业务参数；响应沿用统一成功标志、错误码、消息与数据结构。需要补充的错误码包括 `UNAUTHENTICATED`、`SESSION_EXPIRED`、`PERMISSION_DENIED`、`ACCOUNT_FROZEN`、`LAST_SUPER_ADMIN_PROTECTED` 和 `TOO_MANY_LOGIN_ATTEMPTS`。

### 5.4 管理端 UI

- 登录页：明确显示账号冻结、认证失败和会话过期，不暴露内部安全细节。
- 管理员页：列表、状态、角色分配；危险动作二次确认。
- 角色权限页：MVP 可只读展示五种内置角色的权限矩阵。
- 活动会话页：查看并撤销指定管理员会话；时间不足时可合并到管理员详情。
- 审计页：按条件分页筛选，查看动作、对象、结果和脱敏后的关键变化。
- 全局交互：登录后缓存服务端返回的权限集合以控制菜单；收到权限变化或会话失效错误后刷新身份或回到登录页。

## 6 按顺序实施步骤

### 步骤 0：仓库勘察与基线确认

**产出：** 找到真实服务端入口、管理端工程、共享协议、管理员表、数据库初始化与扩展建表脚本、测试命令；记录当前管理员登录链路和敏感管理动作清单，给出不超过 8 条的短计划。

**验证：** 原项目按仓库说明能够构建或启动；若核心源码未入库，停止编码并报告缺口，不能在示例工程中伪造实现。

### 步骤 1：扩展建表与初始化数据

**产出：** 在现有数据访问边界内补充角色、权限、分配、会话和审计数据结构；写入五种内置角色、权限集合和加密后的 `admin / 123456` 演示账号。

**验证：** 空数据库可一次初始化；重复初始化不报错、不产生重复角色；数据库中搜索不到明文密码和完整令牌。

### 步骤 2：登录、会话与退出

**产出：** 密码摘要验证、随机令牌、令牌摘要落库、到期检查、主动退出、冻结检查和基础登录失败限制。

**验证：** 正确密码可登录；错误密码、冻结账号、过期令牌和已退出令牌分别返回稳定错误码；服务端日志不打印密码和令牌。

### 步骤 3：统一服务端鉴权

**产出：** 集中的“动作—权限”注册表和请求分发前鉴权入口；现有管理动作逐一登记权限，未登记动作默认拒绝。

**验证：** 使用低权限账号直接构造高权限 Socket 请求仍被拒绝；被拒绝请求没有数据库副作用；超级管理员原有核心管理流程仍可运行。

### 步骤 4：角色分配与在线权限变化

**产出：** 管理员列表、角色查询和角色分配服务；权限版本或会话撤销机制；最后一个超级管理员保护和禁止自提权。

**验证：** 角色变更后不重启服务即可生效；普通管理员无法提权；移除最后一个有效超级管理员角色被拒绝且数据未改变。

### 步骤 5：审计写入与脱敏

**产出：** 统一审计接口；接入登录、角色分配及仓库中已经存在的敏感操作；记录成功、业务失败和越权失败。

**验证：** 每个目标动作都能用 `requestId` 关联到唯一审计记录；前后值只包含必要字段；密码、令牌和密钥不会进入数据库或界面。

### 步骤 6：管理端页面

**产出：** 权限驱动的菜单/按钮、管理员角色分配界面和审计分页查询界面；按现有 UI 风格复用控件与网络封装。

**验证：** 不同角色看到的操作入口正确；界面权限与服务端权限一致；会话过期可回到登录页；分页、筛选和空状态可用。

### 步骤 7：回归、文档与演示数据

**产出：** 模块自动化测试或项目现有测试框架中的对应测试；更新必要的初始化/运行说明；准备两类管理员测试账号和可重复演示步骤。

## 7 测试矩阵

| 类型 | 场景 | 预期结果 |
| --- | --- | --- |
| 正常 | 超级管理员登录并分配运维角色 | 登录成功，角色事务提交，目标账号权限生效，产生审计记录 |
| 授权 | 运维人员处理工单或重启设备 | 服务端允许已授权动作 |
| 越权 | 运维人员直接请求价格修改 | 返回 `PERMISSION_DENIED`，价格无变化，记录越权审计 |
| 认证 | 错误密码连续登录 | 登录失败；达到阈值后触发短时限制；不泄露账号是否存在的额外信息 |
| 状态 | 冻结已登录管理员 | 后续请求被拒绝，活动会话失效 |
| 会话 | 过期、退出或被撤销的令牌再次请求 | 返回稳定认证错误，无业务副作用 |
| 角色 | 在线移除某项权限 | 下一次请求即拒绝，或会话被撤销并要求重新登录 |
| 保护 | 尝试冻结或降级最后一个超级管理员 | 返回保护错误，事务回滚 |
| 幂等 | 相同 `requestId` 重复提交高风险动作 | 业务只执行一次，返回一致结果 |
| 审计 | 查询成功、失败和越权记录 | 可按条件分页检索，排序稳定，敏感字段已脱敏 |
| 并发 | 两个请求同时修改同一管理员角色 | 不产生重复关联，不绕过最后超级管理员保护 |
| 回归 | 普通用户手机号登录和核心订单流程 | 行为与模块改造前一致 |

## 8 Definition of Done

以下条件全部满足才算模块完成：

- [ ] 服务端对所有已存在的管理写动作执行统一认证和权限校验。
- [ ] 至少五种内置角色及权限关系可重复初始化，数据库无明文密码和完整令牌。
- [ ] 冻结、退出、过期、角色变化和最后超级管理员保护均按约束生效。
- [ ] 至少登录、角色分配、用户冻结/解冻、价格修改、退款/余额调整、电桩重启中的“仓库已实现项”接入审计；未实现的业务不得为满足清单而伪造。
- [ ] 审计记录可分页查询，并包含成功、失败和越权结果，敏感字段已脱敏。
- [ ] 管理端可完成登录、查看自身权限、角色分配和审计查询；无权限按钮不可操作。
- [ ] 数据变更具备事务、唯一约束或幂等保护，重启服务后仍然有效。
- [ ] 相关构建、自动化测试和核心流程冒烟测试通过。
- [ ] 提交说明列出实际修改文件、扩展建表脚本、协议变化、测试命令与结果，以及仍保留的限制。

## 9 风险与降级

| 风险 | 优先处理 | 可接受降级 |
| --- | --- | --- |
| 现有接口分散，难以统一鉴权 | 先在 Socket 分发入口建立单一检查点，再逐动作登记 | 只覆盖当前确实存在的管理动作，但未登记动作必须默认拒绝 |
| 动态角色编辑扩大范围 | 保留表结构和内置角色数据 | MVP 只读展示固定五种角色，不提供新建、删除角色 |
| 权限缓存失效复杂 | 每次请求比对权限版本 | 角色变化后撤销目标管理员全部会话并要求重新登录 |
| 安全库缺失 | 复用 Qt/项目依赖中的成熟实现或引入范围明确的实现 | 使用 PBKDF2-HMAC-SHA256；不得降级为明文、固定盐或普通单次哈希 |
| 审计前后快照过大 | 为每个动作定义白名单字段 | 只保存关键字段摘要，但保留操作者、动作、对象、结果、错误码和时间 |
| 登录限流持久化成本高 | 使用 `login_attempt` 并定期清理 | 单进程内短时限流；必须在重启后明确清零且写入限制说明 |

任何降级都不能取消服务端鉴权、密码安全存储、最后超级管理员保护和关键操作审计。
