# 04 · 智能排队与候补预约

## 1 文档用途

本文是扩展模块 04 的任务规格。技术底座、命令字分段、单位口径、接缝规则见 [00-扩展功能模块实施路径推荐.md](00-扩展功能模块实施路径推荐.md) 第 4、5 节；**凡本文第 5 节与 00 第 4 节冲突，以 00 为准**。

本模块在既有预约（1202 / 1206）之外增加「满桩时排队候补」。**正式预约必须调用既有预约服务完成**，以保留未结算拦截（`[说明书]` 1.4 明文）、活动订单保护与事务边界；调度器不得自己拼订单 SQL。

本模块是全部扩展中**并发与超时最密集**的一个，agent 在这类逻辑上最容易写出「看起来对」的代码，建议 **L4** 认领——异常路径回归本就是他的第二顶帽子。

## 3 业务流程

### 3.1 加入队列

1. 用户在某站点、某桩类型没有可预约电桩时选择“加入候补”。
2. 服务端重新检查用户是否冻结、是否有待结算订单、是否有活动订单、是否已有活动队列项或邀请。
3. 服务端再次检查统一可用性；如果此刻已有可预约电桩，应返回“可直接预约”结果，不重复加入队列。
4. 校验通过后创建 `WAITING` 队列项，记录加入时间、最大等待截止时间和单调递增的排队顺序依据。
5. 返回队列编号、前方人数和预计等待时间；预计值必须明确标记为估算。

用户已有活动队列或邀请时，原直接预约入口应返回 `QUEUE_ALREADY_ACTIVE`，由用户先取消候补再预约其他电桩。MVP 不在两个独立事务中“先自动取消队列、再尝试预约”，以免预约失败后用户同时失去候补资格。

### 3.2 电桩释放与队首邀请

1. 电桩由原业务流程恢复为 `IDLE` 后发布可用事件；定时扫描作为漏事件兜底。
2. 调度器按“站点 + 桩类型”串行处理，选择加入时间最早的有效 `WAITING` 用户。
3. 调度前再次检查用户资格，资格已失效则将该队列项结束并记录原因，然后继续下一位。
4. 在同一短事务中，对一个 `IDLE` 且无有效 hold 的电桩创建 `pile_hold`，并创建带随机邀请令牌和截止时间的邀请。
5. 队列项进入 `INVITED`，用户端通过现有推送或主动查询获得邀请和倒计时。

hold 只是调度锁，不是电桩业务状态。邀请阶段电桩仍保持 `IDLE`，但所有“可预约/空闲数”查询必须使用统一条件：电桩为 `IDLE` 且不存在有效 hold。

### 3.3 接受邀请并转换为正式预约

1. 用户提交邀请令牌、`requestId` 或幂等键。
2. 服务端在事务内条件检查：用户资格仍有效、邀请仍为 `OFFERED` 且未过期、hold 仍有效、电桩仍为 `IDLE`、用户无其他活动订单。
3. 调用原预约业务逻辑，在同一事务上下文中创建 `RESERVED` 订单并执行电桩 `IDLE -> RESERVED`。
4. 同一事务中将邀请标记为 `ACCEPTED`、队列项标记为 `CONVERTED`、hold 标记为已消费或失效。
5. 返回正式订单编号；相同幂等键重复确认必须返回同一订单，不能再创建一单。

若现有预约服务无法参与调用方事务，应先做最小重构，把“预约校验和写入”提取为可接收事务上下文的内部方法；不能复制一份预约 SQL。

### 3.4 拒绝、超时与异常撤回

- 用户拒绝邀请：邀请进入 `REJECTED`，队列项进入 `CANCELLED`，释放 hold 并调度下一位。
- 用户未在时限内响应：邀请进入 `EXPIRED`，队列项进入 `EXPIRED`，释放 hold 并调度下一位。
- 电桩在邀请期间故障、离线或被原业务占用：邀请进入 `REVOKED`，释放 hold；用户队列项可回到 `WAITING` 并保留原排队顺序，界面说明原因。
- 用户主动取消：等待中直接进入 `CANCELLED`；已邀请时同时撤销邀请并释放 hold。
- 用户资格在等待中失效：队列项进入 `CANCELLED`，事件原因记录为资格失效，不创建订单。

### 3.5 查询、重连与替代站点

用户端每次登录或断线重连后向服务端查询当前队列/邀请，不能只依赖本地倒计时。服务端返回自己的当前时间和邀请截止时间，客户端只负责显示。

替代站点查询只返回当前业务数据，过滤不可服务站点，再按距离、有效空闲数和价格进行稳定排序。用户选择替代站点后仍走原预约或入队流程，不能自动替用户下单；若用户已有活动候补，界面应先提示其取消当前候补。

## 4 状态与不可破坏约束

### 4.1 队列状态

主要迁移：

`WAITING -> INVITED -> CONVERTED`

终止迁移：

- `WAITING -> CANCELLED / EXPIRED`
- `INVITED -> CANCELLED / EXPIRED`
- `INVITED -> WAITING` 仅限邀请因电桩不可用被系统撤回，必须记录原因且保留原排队顺序

`CONVERTED / CANCELLED / EXPIRED` 为终态。

### 4.2 邀请状态

`OFFERED -> ACCEPTED / REJECTED / EXPIRED / REVOKED`

所有终态不可回退；再次邀请必须创建新的邀请记录和令牌。

### 4.3 hold 状态

若采用保留历史记录的实现，建议：

`ACTIVE -> CONSUMED / RELEASED / EXPIRED`

也可在事务成功后删除 hold，但必须保留对应队列事件和邀请结果。无论采用哪种方式，一个电桩同时最多只能有一个有效 hold。

### 4.4 不可破坏约束

1. 排队期间不创建订单；只有邀请接受成功才生成一个 `RESERVED` 订单。
2. 邀请期间不修改电桩状态；hold 不能新增成电桩状态字符串。
3. 不修改既有订单状态与电桩状态。**电桩只有在用/闲置/故障三态**，本模块的 hold **必须落在独立表**，禁止给 `t_pile.status` 加第四个值；详见 [00 第 4.5.1 节状态命名映射](00-扩展功能模块实施路径推荐.md)。
4. 一个用户最多存在一个活动队列项或一个活动邀请；同时不得存在与资格规则冲突的活动订单。原直接预约入口也必须检查活动候补并提示先取消，避免跨入口绕过限制。
5. 一个电桩最多存在一个有效 hold；普通预约和队列调度都必须使用同一个“`IDLE` 且无有效 hold”的可用性判断。
6. 接受邀请必须复用原预约服务，并在一个事务中完成订单创建、电桩状态迁移、邀请接受、队列转换和 hold 消费/失效。
7. 超时线程、用户确认、用户取消和设备状态变化必须采用条件更新竞争，任一时刻只能一个分支成功。
8. 队列严格按服务端记录的加入顺序处理；若跳过用户，必须记录明确、可查询的资格失败原因。
9. 服务重启后必须清理过期 hold、完成过期邀请并恢复调度，不能出现永久占位。
10. 未结算订单拦截、冻结用户检查和活动订单检查必须在加入、发出邀请和接受邀请三个时点重复执行。
11. hold、邀请和队列项进入 `INVITED` 必须原子提交；任何一步失败都不得留下孤儿 hold 或没有 hold 的有效邀请。

## 5 建议架构、数据、协议与 UI

### 5.0 技术路线校准（对齐真实仓库）

| 原文档设计 | **校准后落地** | 为什么 |
| --- | --- | --- |
| 电桩状态含 `RESERVED` | **禁止。** `[说明书]` 1.4 明文只有在用/闲置/故障三态。「被 hold 占住」是**独立的 `t_queue_hold` 表**，可用性判定 = `t_pile.status = 1(闲置)` **且** `t_pile.online = 1` **且** 无有效 hold **且** 该桩无活动订单（`t_order.status IN (0,1,2)`） | 加第四个状态值会让 2303「电桩状态分布」当场失真，并违反 `[说明书]` 明文，见 00 第 4.5.1 节 |
| `queue_config` 表 | **不建表。** `queue_offer_sec`（邀请有效期）、`queue_max_wait_sec`（最大等待）、`queue_enabled_stations` 放 `t_sys_config` | 配置项只有三个 |
| 邀请令牌落库摘要 | 沿用会话 token 的同款做法：**32 位 hex 明文只回给当前客户端，库里存 SHA-256** | 与协议 §6 一致，`QCryptographicHash` 已在 `admin_service.cpp` 用过 |
| 正式预约由调度器直接写订单 | **必须调用 `server/biz/reservation_service.cpp` 已有的预约逻辑**（提取一个内部函数供本模块调用，或由 L2 暴露一个内部接口——**这一步要先和 L2 对齐**） | 未结算拦截、冻结校验、活动订单保护都在那里；绕过它就等于第二套预约系统 |
| 队列事件推送 | 用 **B2 推送通道**（`3380` 推送邀请）；**同时必须提供 `3302 QUEUE_STATUS` 主动查询作为兜底** | 用户端可能断线、可能在后台；本地倒计时结束后一律以服务端响应为准（原文已如此要求，保留） |
| `requestId` | 放 `data.reqId`，配合 `t_queue_offer` 上的 `UNIQUE(req_id)` | 见 00 第 4.6 节 |
| 新增 `USER_NOT_ELIGIBLE` / `RESERVATION_CONFLICT` | **复用已有码**：账号冻结 `2003`、存在未结算订单 `4002`、电桩被占 `3003`、电桩故障 `3004` | 见 00 第 4.3 节 |

**并发要点（本模块最容易错的地方）**：

- 调度按 `station_id + pile_type` **串行**：同一分组同一时刻只允许一个调度动作。SQLite 层面用 `BEGIN IMMEDIATE` + 条件更新兜底，服务层再加一把按分组的互斥锁。
- 「接受邀请 → 消费 hold → 建正式预约」必须在**同一事务**内；任一步失败整体回滚，hold 归还队列。
- 同一用户**同时只能有一份有效邀请**：`t_queue_offer` 上建部分唯一索引 `WHERE status = 0`。
- 服务重启后：定时任务启动时先扫一遍过期 hold 与过期邀请并清理，**不依赖内存状态**。

**命令字登记表**：

| 命令字 | 常量名 | 方向 | `data` |
| --- | --- | --- | --- |
| 3300 | `CMD_EXT_QUEUE_JOIN` | 用户端 | `{stationId, pileType, reqId}` |
| 3301 | `CMD_EXT_QUEUE_CANCEL` | 用户端 | `{entryId, reqId}` |
| 3302 | `CMD_EXT_QUEUE_STATUS` | 用户端 | `{}` → `{entry, aheadCount, etaSec, offer}` |
| 3303 | `CMD_EXT_OFFER_RESPOND` | 用户端 | `{offerId, token, accept, reqId}` → 接受时返回 `{orderId}` |
| 3304 | `CMD_EXT_ALT_STATION` | 用户端 | `{stationId, lng, lat}` → 替代站点（距离/空闲/价格固定排序） |
| 3340 | `CMD_EXT_QUEUE_ADMIN_LIST` | 管理端 | `{page, size, stationId}` |
| 3341 | `CMD_EXT_QUEUE_METRICS` | 管理端 | `{}` → 等待人数、平均等待、邀请接受率、转化率 |
| 3380 | `CMD_EXT_QUEUE_OFFER_PUSH` | **服务端推送** | `{offerId, token, pileId, pileCode, deadline}`，`seq=0, code=0` |

**错误码登记表**：`6301 ERR_QUEUE_ACTIVE`（已在队列中）、`6302 ERR_QUEUE_UNAVAILABLE`（该站未启用/无可排队桩型）、`6303 ERR_OFFER_EXPIRED`、`6304 ERR_OFFER_RESPONDED`、`6305 ERR_HOLD_CONFLICT`。

**建表脚本 `docs/db-schema-ext-04.sql`**：`t_queue_entry`（`user_id, station_id, pile_type, seq_no, join_time, deadline, status, end_reason, update_time`；部分唯一索引 `WHERE status = 0` 保证一人一队）、`t_queue_offer`（`entry_id, pile_id, token_hash, status, send_time, deadline, respond_time, order_id, req_id UNIQUE`）、`t_queue_hold`（`pile_id, entry_id, offer_id, deadline, valid`；部分唯一索引 `WHERE valid = 1` 保证一桩一 hold）、`t_queue_event`（只增不改）。

**等待估算**：`预计等待 = 前方有效人数 × 同类型历史平均占用秒 ÷ 可服务桩数`。历史平均取 `t_order` 中该站该桩型已结算订单的 `strftime('%s', end_time) - strftime('%s', start_time)` 均值；样本不足时用 `t_sys_config.queue_default_dwell_sec`，并在界面标注「估算」。设置合理上下限，**不承诺实际开始时间**。

### 5.1 服务端组件

- `QueueService`：加入、取消、状态查询、资格检查和队列事件。
- `QueueScheduler`：按站点和桩类型串行匹配队首用户与可用电桩。
- `PileHoldService`：原子创建、查询、消费、释放和过期清理 hold。
- `QueueOfferService`：邀请令牌、响应、幂等确认和正式预约转换。
- `QueueTimeoutWorker`：处理最大等待、邀请超时和过期 hold。
- `AlternativeStationService`：固定规则筛选和排序替代站点。
- `PileAvailabilityService`：统一封装“核心状态 + 有效 hold”的可用性；若仓库已有同类服务，应直接扩展而不是新建重复入口。

调度器不能直接拼接订单 SQL。正式预约必须经过原业务服务，以保留未结算拦截、活动订单保护、事务和审计。

### 5.2 建议数据

- `queue_entry`：用户、站点、桩类型、加入序号/时间、最大等待截止、状态、终止原因、更新时间。
- `queue_offer`：队列项、电桩、令牌摘要、状态、发出/截止/响应时间、关联订单编号、`requestId`。
- `pile_hold`：电桩、队列项、邀请、状态或有效标志、创建/截止时间、版本。
- `queue_event`：队列项、事件、前后状态、原因、关联对象、时间，只新增不覆盖。
- `queue_config`：站点、启用状态、邀请有效秒数、最大等待时长；MVP 可由初始化数据提供默认值。

令牌数据库字段保存摘要而非可直接使用的邀请令牌。活动队列、活动邀请和有效 hold 应使用部分唯一索引或等价数据库约束兜底；为“站点 + 桩类型 + 状态 + 加入顺序”、截止时间和用户建立索引。扩展建表脚本需幂等。

### 5.3 调度和等待估算

基础调度键为“站点 + 桩类型”，组内按服务端加入序号或“加入时间 + 主键”稳定排序。多台电桩同时空闲时可以循环匹配，但同一用户只能获得一份有效邀请。

基础等待时间可按以下方式估算：

`预计等待时间 = 前方有效人数 × 同类型历史平均占用时长 ÷ 可服务电桩数`

数据不足时使用明确配置的默认占用时长，并在界面显示“估算”。极端值应设置合理上下限，不承诺实际开始时间。

### 5.4 建议协议动作

- `QUEUE_JOIN`、`QUEUE_CANCEL`、`QUEUE_STATUS`。
- `QUEUE_OFFER_RESPOND`。
- `QUEUE_CONFIG_QUERY`、`QUEUE_CONFIG_UPDATE`。
- `QUEUE_ADMIN_LIST`、`QUEUE_METRICS_QUERY`。
- `ALTERNATIVE_STATION_QUERY`。
- 队列邀请事件或统一消息通知；若现有协议无推送，则通过 `QUEUE_STATUS` 主动查询。

沿用项目现有 Socket 消息封装、认证、`requestId`、分页和错误响应。建议补充 `QUEUE_ALREADY_ACTIVE`、`QUEUE_NOT_AVAILABLE`、`OFFER_EXPIRED`、`OFFER_ALREADY_RESPONDED`、`PILE_HOLD_CONFLICT`、`USER_NOT_ELIGIBLE` 和 `RESERVATION_CONFLICT`。

### 5.5 用户端、管理端和 Web UI

用户端：

- 站点满桩时展示“加入候补”，并明确桩类型。
- 当前队列页显示前方人数、预计等待、加入时间和取消按钮。
- 邀请弹窗显示电桩摘要、服务端截止时间、接受/拒绝和倒计时。
- 登录、前台恢复和断线重连时查询服务端状态；本地倒计时结束后以服务端响应为准。
- 邀请失效时给出原因，并可查询替代站点。

管理端：

- 按站点和桩类型查看等待人数、活动邀请、超时情况。
- 配置是否启用、邀请有效期和最大等待时间；写操作需要权限和审计。
- MVP 不提供拖拽改序、人工插队或直接替用户确认。

Web 大屏可增加当前排队人数、平均等待时间、邀请接受率和候补转预约率，均从队列事件和订单事实聚合。

## 6 按顺序实施步骤

### 步骤 0：仓库勘察与事务边界确认

**产出：** 定位预约服务、电桩状态机、可用性查询、用户资格校验、订单事务、扩展建表脚本、用户端网络层和测试命令；画出原预约的真实调用链并给出不超过 8 条的短计划。

**验证：** 原预约、取消和未结算拦截可运行；若核心源码未入库，报告缺口并停止，不在示例 Socket 工程中伪造业务。

### 步骤 1：数据结构与集中状态机

**产出：** 队列、邀请、hold、事件的扩展建表（配置放 `t_sys_config`）；集中实现本文规定的合法状态迁移与终止原因。

**验证：** 空库/已有库迁移和重复初始化成功；唯一约束可阻止同一用户多个活动队列和同一电桩多个有效 hold。

### 步骤 2：加入、查询与取消

**产出：** 复用用户资格检查，实现 `QUEUE_JOIN / STATUS / CANCEL`；返回稳定排队顺序、前方人数和基础估算；为原直接预约入口补充活动候补冲突检查。

**验证：** 冻结用户、有待结算订单、有活动订单、重复入队和已有可预约电桩的情况都得到正确结果；等待中取消后不再被调度；有活动候补时直接预约会提示先取消且不破坏候补。

### 步骤 3：统一可用性与 hold

**产出：** 在原电桩可用性入口中加入“无有效 hold”条件；实现原子创建、释放、消费和过期 hold。

**验证：** 普通预约与调度器竞争同一电桩时只能一方成功；站点空闲数不包含被 hold 的电桩；hold 不改变电桩状态。

### 步骤 4：FIFO 调度、邀请与超时

**产出：** 按站点/桩类型串行调度；创建邀请令牌、截止时间、倒计时数据；实现拒绝、超时和顺延。

**验证：** 两名用户按顺序入队，第一名超时后释放 hold，第二名收到邀请；快充和慢充队列互不串线。

### 步骤 5：接受邀请与正式预约事务

**产出：** 将原预约逻辑抽取为可在既有事务中复用的内部能力；一个事务完成正式订单、电桩 `IDLE -> RESERVED`、邀请、队列和 hold 更新；实现幂等响应。

**验证：** 正常确认只生成一单；重复确认返回同一订单；确认与超时并发时只有一方成功；任一步失败时事务全部回滚。

### 步骤 6：事件触发、断线和服务重启恢复

**产出：** 接入电桩释放事件并增加周期扫描兜底；用户重连恢复；服务启动时处理过期邀请/hold并重新调度。

**验证：** 漏掉一次释放事件仍能通过扫描继续；客户端断线不丢队列；在活动邀请期间重启服务后无永久 hold、无重复订单。

### 步骤 7：用户端闭环

**产出：** 满桩入口、当前队列、邀请倒计时、接受/拒绝、失效提示和重连查询；沿用现有 Qt 模型、Socket 客户端和 UI 风格。

**验证：** 完整演示不需要手工改数据库；服务端时间与客户端倒计时偏差不会使过期邀请被接受；错误和空状态可理解。

### 步骤 8：管理查询、推荐、指标与回归

**产出：** 最小管理查询/配置，固定规则替代站点推荐，基础指标，自动化测试和可重复演示数据。

**验证：** 配置修改有权限与审计；推荐使用真实站点数据；指标可查询复核；原直接预约、取消预约、开始充电和待结算拦截通过回归测试。

## 7 测试矩阵

| 类型 | 场景 | 预期结果 |
| --- | --- | --- |
| 正常 | 满桩后加入队列 | 创建唯一 `WAITING` 项，返回前方人数和估算时间，不创建订单 |
| 直接预约 | 加入请求到达时已有可用桩 | 不加入队列，提示走原预约流程 |
| 资格 | 冻结、有待结算或有活动订单的用户入队 | 返回 `USER_NOT_ELIGIBLE`，不创建队列项 |
| 重复 | 同一用户重复入队或多端同时入队 | 最多一个活动队列项，返回可查询的现有状态 |
| 跨入口 | 已排队用户直接预约其他电桩 | 返回 `QUEUE_ALREADY_ACTIVE`，不创建订单也不自动取消候补 |
| FIFO | 两名用户依次入队，一台桩释放 | 第一名先获邀请；顺序有稳定数据库依据 |
| 类型隔离 | 快充用户排队但只释放慢充桩 | 快充用户不获错误邀请，慢充队列可正常调度 |
| 超时顺延 | 第一名邀请超时 | 邀请/队列过期，hold 释放，第二名获邀 |
| 拒绝 | 第一名主动拒绝 | 队列取消、hold 释放，下一名获邀 |
| 电桩异常 | 邀请期间电桩变为故障/离线 | 邀请撤回，hold 释放，用户回到等待或收到明确终止原因 |
| 原子转换 | 用户接受有效邀请 | 只创建一个 `RESERVED` 订单，电桩进入 `RESERVED`，队列转为 `CONVERTED` |
| 幂等 | 相同 `requestId` 多次确认 | 返回同一订单，不重复扣资源或建单 |
| 竞争 | 确认、超时、取消同时发生 | 只有一个条件更新分支成功，无孤儿 hold 或重复订单 |
| 可用性 | 普通预约与候补同时抢一台桩 | 只有一方成功；有效空闲数不包含 hold |
| 重连 | 用户收到邀请后断线再登录 | 从服务端恢复剩余时间和邀请状态 |
| 服务重启 | 活动邀请/hold 期间重启 | 过期项被清理，有效项可恢复，无永久 hold |
| 回归 | 原直接预约、取消、充电、结算 | 行为与加入队列模块前一致，核心状态字符串不变 |

## 8 Definition of Done

- [ ] 无空闲桩时用户可按站点和桩类型加入、查询和取消唯一队列项。
- [ ] 排队和邀请阶段不创建订单，也不新增或改变电桩核心状态。
- [ ] 调度按稳定 FIFO 顺序运行，并在每次调度时重新检查用户资格。
- [ ] 原直接预约入口会阻止活动候补用户绕过限制，并提示先取消候补。
- [ ] 所有电桩可用性查询统一排除有效 hold，数据库约束阻止重复 hold。
- [ ] 邀请具有服务端截止时间、接受、拒绝、超时和系统撤回处理。
- [ ] 接受邀请复用原预约服务，在一个事务中完成订单、电桩、邀请、队列和 hold 变化。
- [ ] 重复确认、确认/超时竞争和普通预约/候补竞争不会生成重复订单或冲突状态。
- [ ] 用户端可完整演示加入、等待、倒计时、确认及重连恢复。
- [ ] 服务重启可清理过期 hold 并恢复调度，不需要人工改数据库。
- [ ] 管理配置受权限和审计保护，基础指标和推荐来自统一真实数据。
- [ ] 相关构建、自动化测试及原预约/充电/结算回归测试通过。
- [ ] 最终报告列明实际修改文件、协议/数据库变化、验证命令和剩余限制。

## 9 风险与降级

| 风险 | 优先处理 | 可接受降级 |
| --- | --- | --- |
| 原预约服务事务不可复用 | 提取共享内部方法并让调用者传入事务上下文 | 暂停确认功能并报告阻塞；不得复制 SQL 或使用补偿逻辑伪装原子性 |
| SQLite 并发写竞争 | 按站点/桩类型串行调度，使用短事务和条件更新 | 全局单调度线程；唯一约束仍作为最终防线 |
| 推送丢失 | 推送只作提醒，服务端查询为事实来源 | 用户端短周期查询 `QUEUE_STATUS`，前后台切换时立即刷新 |
| 本地时钟偏差 | 响应返回服务端时间和截止时间，服务端最终判定过期 | 客户端只显示近似倒计时，不本地决定接受成功 |
| 等待时间误差 | 使用历史平均、合理上下限并明确“估算” | 只展示前方人数，不显示预计分钟数 |
| 服务重启留下 hold | 启动恢复和周期过期清理 | 短有效期 + 每次可用性查询惰性清理；仍必须有自动恢复路径 |
| 功能范围膨胀 | 首期固定 FIFO 和站点/桩类型两个维度 | 管理端只读队列和修改两个时间参数；高级推荐、大屏指标延后 |

任何降级都不能牺牲正式预约事务原子性、唯一活动 hold、未结算拦截和核心状态兼容性。
