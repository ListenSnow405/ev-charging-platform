# 06 · 智能充电与站点能源管理

## 1 文档用途

本文是扩展模块 06 的任务规格。技术底座、命令字分段、单位口径、接缝规则见 [00-扩展功能模块实施路径推荐.md](00-扩展功能模块实施路径推荐.md) 第 4、5 节；**凡本文第 5 节与 00 第 4 节冲突，以 00 为准**。

本模块在站点容量约束下，把有限功率**确定性地**分给正在充电的会话，并把 `t_load_forecast` 的 1/6/24 小时预测变成运营端负荷预警——正好落在 `[说明书]` 1.4「为运营端提供负荷预警，辅助提前做好电力调配」这句话上。

建议 **L5** 认领（预测数据与大屏同源）或 **L1**（设备命令通道是他的）。**功率下发必须复用模块 02 的设备命令服务，不得另建旁路 socket。**

## 3 业务流与数据流

### 3.1 计划预览

```text
管理员请求预览 / 调度定时器触发
  -> 读取站点策略及其版本
  -> 读取同一数据截止时间下的其他负荷、设备能力、最新遥测
  -> 由订单查询服务返回合法 CHARGING 会话
  -> 生成不可变输入快照
  -> C++ 基线算法计算各会话目标功率
  -> 服务端执行硬约束校验
  -> 保存 GENERATED 计划及分配明细
  -> 管理端展示约束、理由和调度前后结果
```

预览不下发设备命令，也不改变任何订单、电桩或钱包状态。

### 3.2 计划应用与反馈

```text
管理员应用计划 / 自动模式触发
  -> 重新校验策略版本、活动订单版本、设备在线状态和遥测新鲜度
  -> 将计划原子标记为待应用
  -> 逐设备通过设备命令服务发送 SET_POWER_LIMIT
  -> 模拟设备返回 ACK、执行结果和实际功率
  -> 记录每项 APPLIED / FAILED 反馈
  -> 失败项使用上一个安全值或配置的安全值，并触发下一轮重算
```

计划应用是幂等操作。重复点击或服务重试不能生成多组相互覆盖的有效命令。

### 3.3 周期调度和预测预警

```text
每 5～15 秒收集实际负荷
  -> 检测订单开始/结束、设备故障/离线、策略变更
  -> 有变化时重算当前计划

定时读取未来 1/6/24 小时预测
  -> 服务端校验预测时间、版本和置信信息
  -> 与容量及预警阈值比较
  -> 生成 OPEN 告警或更新已有告警
  -> 管理端/Web 展示，不直接执行订单动作
```

预测服务不可用时，仅缺少未来预警；当前功率分配继续使用实际快照和基线算法。

## 4 状态与不可破坏约束

### 4.1 状态定义

- 功率计划：`GENERATED -> APPLYING -> APPLIED -> COMPLETED`，异常终态为 `FAILED / CANCELLED`。
- 分配明细：`PENDING -> SENT -> APPLIED`，异常为 `FAILED / SKIPPED`。
- 负荷告警：`OPEN -> ACKED -> RESOLVED`。
- 订单和电桩继续使用项目统一状态，不引入能源模块专属订单状态。

### 4.2 不变量

1. 只有权威状态为 `CHARGING` 的订单可以获得非零充电目标功率。
2. `sum(target_power_w)` 不得超过当前安全可用功率；单桩目标不得超过设备额定功率、会话请求上限和策略上限中的最小值。
3. 功率、能量和比例分别使用整数 W、Wh 和基点，禁止用浮点数持久化关键约束。
4. 同一站点同一时间最多有一个当前应用计划；计划必须绑定策略版本和输入快照版本。
5. 应用前必须重新检查订单、电桩、设备、连接世代和策略版本；过期计划只能取消或重新预览。
6. 已结束订单、故障/离线电桩不得收到旧计划命令；停止充电命令优先于功率限制命令。
7. 模型输出必须经过同一套服务端硬约束裁剪；模型不能直接发送设备命令或写数据库。
8. 调度失败不能推进或回退订单状态，不能更改订单金额，也不能阻止用户停止和结算。
9. 设备不应答时只能保持已知安全值或降到配置安全值，不能假设命令已经执行。

## 5 建议实现设计

### 5.0 技术路线校准（对齐真实仓库）

| 原文档设计 | **校准后落地** | 为什么 |
| --- | --- | --- |
| 功率用 W 整数、能量用 Wh | **功率 kW（`REAL`）、能量 `kwh_x100`** | `t_pile.power`、`t_load_forecast.load_kw` 均为 REAL kW，见 00 第 4.5 节 |
| `SET_POWER_LIMIT` 动作名 | **设备命令字 `9011`**，属于模块 02 的设备段 `9005–9049`。使用前**与 02 认领人对齐并登记到 [CLAIM.md](CLAIM.md)** | 跨模块占号必须有登记，否则两人会同时用同一个号 |
| `charge_demand` 表 | **MVP 不建表。** 每个会话的需求上限 = `min(t_pile.power, t_sys_config.energy_default_demand_kw)`；目标电量与预计离场时间列为增强项 | 用户端没有「我要充到多少度、几点走」的输入，建了也没数据来源 |
| `station_energy_sample` 表 | 保留为 **`t_energy_sample`**，但 MVP 的「其他负荷」取 `t_sys_config.energy_other_load_kw` 固定值 | 项目没有站点电表，其他负荷无真实来源；固定值可演示且可解释 |
| `LoadPredictionAdapter` 带超时读取预测 | **直接只读 `t_load_forecast`**（同一个 SQLite 库，`ml/predict.py` 离线回写），不需要超时与进程间调用 | 预测不是在线服务；`horizon` 取 1/6/24，取同一 `model_version` 下 `create_time` 最大的一批（与 2305 口径一致） |
| Python 优化器返回候选分配 | **MVP 不引入。** 基线算法用 C++ 确定性加权 water-filling（原文 5.3 步骤保留，单位换成 kW） | 任务卡已列为非目标；引入跨语言在线调用是本模块最大的范围膨胀风险 |
| 「调度锁按 station_id 粒度」 | 保留。**不要持有数据库事务等待设备响应**：先提交计划与命令意图（`t_dev_cmd`），反馈异步收集 | SQLite 单写者，持事务等网络会把整个服务端写操作堵住 |
| 预测/统计反写业务表 | **禁止**。本模块只写自己的 `t_energy_*` 表与 `t_dev_cmd`，不改 `t_order`、`t_user.balance`、`t_pile.status` | 00 第 3 节明文 |

**分配算法的整数处理**：功率是 `REAL` kW，但下发给设备的限值建议**保留一位小数**（`round(x*10)/10`），并在计划里记录下发值；否则「计划 12.3456 kW / 设备执行 12.3 kW」会让调度前后对比对不上。

### 5.1 架构

先映射到仓库现有分层，以下名称仅表示职责，不要求创建同名路径或类：

- `StationSnapshotProvider`：在一致的数据截止时间读取策略、其他负荷、活动会话、设备能力和遥测。
- `BaselinePowerAllocator`：纯函数式确定性算法，输入快照、输出分配及解释信息，便于单元测试。
- `PowerPlanService`：生成、保存、版本校验、应用、取消和完成计划。
- `PowerCommandAdapter`：复用设备命令服务下发 `SET_POWER_LIMIT`，不另建旁路 Socket。
- `LoadPredictionAdapter`：带超时和模式校验地读取既有预测；失败返回“预测不可用”，不抛垮调度主循环。
- `LoadAlertService`：去重生成 1、6、24 小时预警并管理确认/解除。
- `EnergyQueryService`：向 Qt 管理端和 Web 返回当前快照、计划、反馈和对比指标。

调度锁按 `station_id` 粒度实现。不要持有数据库事务等待设备网络响应；先提交计划和命令意图，再异步收集反馈。

### 5.2 数据

| 实体 | 必要字段 |
|---|---|
| `station_energy_policy` | 站点、容量上限 W、安全裕量 W、默认保障功率 W、调度周期、模式、版本、启用状态 |
| `station_energy_sample` | 站点、采样时间、电网输入 W、充电负荷 W、其他负荷 W、可选光伏/储能 W、质量标记 |
| `charge_demand` | 订单、目标电量 Wh、预计离场、最大功率 W、业务优先级、更新时间/版本 |
| `power_plan` | 站点、周期、状态、算法/策略版本、输入截止时间、可用功率、创建原因、幂等键 |
| `power_allocation` | 计划、订单、电桩、目标功率、旧功率、实际功率、分配理由、执行状态、命令编号 |
| `load_alert` | 站点、预测窗口、阈值、预测峰值、级别、状态、预测版本、首次/最后触发时间 |

计划必须保存计算时的关键约束快照，保证事后可以解释“为什么某个电桩获得该功率”。采样可批量写入，计划头、明细和审计应在同一短事务中提交。

### 5.3 基线算法

MVP 使用确定性加权公平分配，不依赖机器学习：

1. 计算 `available_w = max(0, capacity_w - safety_margin_w - other_load_w)`。
2. 过滤非 `CHARGING`、离线、故障、遥测过期或最大功率小于等于 0 的会话。
3. 对每个会话计算 `cap_i = min(device_rated_w, demand_max_w, policy_per_pile_cap_w)`。
4. 先按每个会话的“软保障功率”分配；若总保障量大于 `available_w`，按权重比例缩放，并用稳定的 `order_id` 顺序分配整数余数。
5. 剩余功率使用加权 water-filling 迭代分配，任何会话达到 `cap_i` 后退出后续轮次。
6. 权重仅使用服务端可信字段，例如业务优先级、预计离场紧迫度和等待时长；缺失数据使用有文档的默认值。
7. 最后再次校验站点总量和单桩上限，生成分配理由、未满足需求和算法版本。

若接入 Python 优化器，它只能返回候选分配，且必须包含请求编号、输入时间窗、算法版本和计算耗时。服务端在严格超时后回退到基线算法，并对任何候选结果执行同样的硬约束校验。

### 5.4 协议和服务接口

沿用统一消息协议，建议增加或复用以下动作：

- `ENERGY_POLICY_GET / ENERGY_POLICY_SET`
- `POWER_PLAN_PREVIEW / POWER_PLAN_APPLY / POWER_PLAN_QUERY`
- `SET_POWER_LIMIT` 及对应 `COMMAND_ACK / COMMAND_RESULT`
- `ENERGY_TELEMETRY_QUERY`
- `LOAD_ALERT_QUERY / LOAD_ALERT_ACK`

预览响应至少包含计划 ID、输入截止时间、策略版本、可用功率、各会话目标、约束说明和 `canApply`。应用请求必须携带计划 ID 与预期版本，避免管理员应用旧页面中的计划。

### 5.5 UI

- 管理端：站点容量/安全裕量配置、当前负荷卡片、计划预览表、人工应用按钮、执行状态、告警列表和失败原因。
- 用户端：只读显示当前实际功率、预计完成时间和“估算”标识，不提供绕过服务端的功率控制。
- Web/ECharts：实际负荷、预测负荷、容量线、各桩功率堆叠、调度前后峰值和 1/6/24 小时风险。

MVP 先交付管理端最小页面；Web 大屏和用户端预计时间可在服务端闭环稳定后补充。

## 7 测试矩阵

| 层级 | 场景 | 关键断言 |
|---|---|---|
| 单元 | 容量为 0、负数配置、其他负荷超过容量 | 输入被拒绝或可用功率为 0；没有负分配 |
| 单元 | 容量充足、容量不足、会话达到上限 | 总分配不越限；单桩不越限；结果可手算 |
| 单元 | 相同输入重复计算、会话顺序变化 | 输出稳定且算法版本一致 |
| 单元 | 整数除法和余数分配 | 无浮点漂移；余数按稳定顺序处理；总和精确 |
| 单元 | 非 `CHARGING`、故障、离线、遥测过期会话 | 目标功率为 0 或被排除，并有明确理由 |
| 集成 | 计划预览 | 数据持久化正确；订单、钱包、电桩权威状态不变 |
| 集成 | 同一计划重复应用 | 只生成一次有效命令，无重复设备动作 |
| 集成 | 应用前订单结束/策略版本变化 | 旧计划被拒绝或取消，重新生成快照 |
| 集成 | 三台设备成功执行 | 实际功率之和不超过安全上限，计划与反馈可关联 |
| 集成 | 一台设备超时/失败 | 其他分配不被回滚；失败项进入明确状态并安全重算 |
| 集成 | 新订单、结束订单、设备故障/恢复 | 一个周期内重算；不向无效会话发送旧命令 |
| 集成 | Python 预测/优化超时、格式错误、越界建议 | 自动回退基线；越界结果被服务端裁剪或拒绝 |
| 并发 | 两个管理员同时应用、定时器同时触发 | 同站点只有一个当前应用计划，无死锁和重复命令 |
| 恢复 | 保存计划后服务重启 | 状态可恢复/收敛；不会误改订单或重复应用 |
| 端到端 | 三台桩额定总功率大于站点容量 | UI 曲线、设备实际值、计划明细一致且始终不越限 |

## 8 Definition of Done

- [ ] 固定演示数据下，三台模拟桩同时充电时总目标功率和实际功率均不超过站点安全上限。
- [ ] 计划预览、应用、反馈和自动重算链路可重复运行，并有可关联的计划 ID、命令 ID 与订单 ID。
- [ ] 调度器和模型不直接写订单、电桩权威状态、钱包、费用或支付数据。
- [ ] 只有 `CHARGING` 会话可获得非零功率，旧计划不会作用于结束、故障或离线会话。
- [ ] C++ 基线算法不依赖 Python，输出确定、可手算、有算法版本和解释信息。
- [ ] 预测/模型超时、格式错误或越界时能安全回退，订单停止与结算不受影响。
- [ ] 重复应用、并发调度和服务重启不会产生多个生效计划或重复命令。
- [ ] 管理端能配置容量、预览/应用计划、查看反馈和告警；估算值有明确标识。
- [ ] 测试矩阵核心场景已自动化并通过，无法执行的测试及原因已记录。
- [ ] 运行说明包含默认配置、固定演示数据、启动顺序、验收步骤和当前非目标。

## 9 风险与降级方案

| 风险 | 识别信号 | 降级方案 |
|---|---|---|
| 设备模块尚未稳定 | `SET_POWER_LIMIT` 无可靠 ACK/结果或无最新遥测 | 先交付“预览模式”，使用只读设备快照；不伪造已执行结果 |
| 预测误差或服务不稳 | 预测超时、版本缺失、值越界 | 当前调度只用实际数据和 C++ 基线；预测页面显示不可用 |
| 算法复杂度失控 | 提前引入线性规划、储能、电价多目标 | 锁定固定容量 + 确定性加权公平；增强项全部延期 |
| SQLite 锁竞争 | 高频采样和计划写入造成延迟 | 采样批量短事务，调度周期调到 10～15 秒，计划关键数据单独提交 |
| 设备执行滞后 | 目标功率和实际功率长时间偏离 | 显示实际值与数据新鲜度；采用上一个安全值并告警，不假设执行成功 |
| 输入数据不足 | 无预计离场或目标电量 | 使用默认权重和会话上限，界面标注默认值；不阻塞公平分配 |
| UI 工作量过大 | 服务端未闭环却开始复杂大屏 | 只保留表格、折线、容量线和预览/应用操作 |
