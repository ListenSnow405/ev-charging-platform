# 08 · 碳减排与能源报告

## 1 文档用途

本文是扩展模块 08 的任务规格。技术底座、命令字分段、单位口径、接缝规则见 [00-扩展功能模块实施路径推荐.md](00-扩展功能模块实施路径推荐.md) 第 4、5 节；**凡本文第 5 节与 00 第 4 节冲突，以 00 为准**。

**本模块是唯一可以在 R0 门禁之前动工的扩展**：它只依赖「已结算订单」这一份历史数据，而 `ml/gen_history.py` 已经按 CR-002 批复播种了历史订单。聚合、报告与导出可以立刻开始做，最后再把管理端页面接上去。

建议 **L5** 认领：`ml/` + `dataviz/` + `export_snapshot.py` 已经是一条成型的离线管道，本模块基本是在它旁边加一段聚合与导出。

## 3 业务流与数据流

### 3.1 基础指标聚合

```text
订单完成 PAID / 定时聚合任务启动
  -> 按数据截止时间读取 PAID 订单最终 Wh、站点、开始/结束时间
  -> 选择站点地区在各时间片生效的排放因子版本
  -> 根据可用数据确定分时拆分方法和质量等级
  -> 使用整数算法计算日/站点指标
  -> 以幂等键写入 carbon_metric_daily 和 calculation_run
  -> 管理端/Web 查询聚合结果
```

权威源只接受 `PAID` 订单。`RESERVED`、`CHARGING`、`PENDING_PAYMENT` 和 `CANCELLED` 不进入正式聚合。

### 3.2 分时电量和能源构成

优先级从高到低：

1. 有可信电表区间数据时，按区间积分并切分峰/平/谷，质量标记为 `METER_INTERVAL`。
2. 只有订单总 Wh 和起止时间时，按各时段重叠时长比例分摊，标记为 `UNIFORM_ESTIMATE`，并把该部分计入估算电量。
3. 起止时间或总 Wh 不完整时，不强行分摊，标记为 `UNAVAILABLE` 并降低完整度。

若接入站点能源构成，优先使用可信的电网、光伏、储能分项。储能放电必须追踪其充电来源；来源未知时归为“来源不明”，不能全部视为零碳。基础版没有能源构成时，可把订单充电电量视为购电量代理，但必须在报告口径中明确这一假设。

### 3.3 报告生成与数据修订

```text
管理员选择站点、日期范围和因子版本
  -> REPORT_PREVIEW 返回指标、口径、完整度和警告
  -> REPORT_GENERATE 保存不可变报告快照
  -> 导出 CSV / 可打印 HTML

迟到 PAID 订单、订单纠正、因子修订或能源数据补录
  -> 标记受影响报告 STALE
  -> 新建 calculation_run 和 report 版本
  -> 保留旧版本，不静默覆盖
```

## 4 状态与不可破坏约束

### 4.1 状态定义

- 计算任务：`PENDING -> RUNNING -> SUCCEEDED`，异常为 `FAILED`。
- 报告：`GENERATING -> READY`，异常为 `FAILED`；源数据变化后为 `STALE`。
- 数据质量：`METER_INTERVAL / UNIFORM_ESTIMATE / UNAVAILABLE`，必要时可复用仓库已有质量枚举，但不得使用含义不清的自由文本。

### 4.2 不变量

1. 报表只读取权威源，任何聚合、预览、导出或重算都不得修改订单、钱包、设备遥测、支付和正式营收。
2. 同一订单在同一计算运行中最多计入一次；取消或未支付订单不得进入指标。
3. 能量使用整数 Wh，排放量使用整数 mgCO2e；中间乘法必须防溢出，舍入规则必须固定并测试。
4. 每个结果必须可追溯到统计范围、数据截止时间、时区、因子 ID/版本/来源、算法版本和质量方法。
5. 因子按生效区间选择，区间统一采用左闭右开 `[start, end)`；重叠因子必须被数据库约束或服务端拒绝。
6. 迟到或纠正数据不能静默覆盖已生成报告，只能把旧版标记 `STALE` 并生成新版本。
7. 用户计费电量与站点侧总能耗必须分开；两者因线路/设备损耗可以不同，不能为了对齐图表而强行相等。
8. “估算减排”不得在缺失比较基准时出现；MVP 页面固定显示“估算电网间接排放，非认证数据”。

## 5 建议实现设计

### 5.0 技术路线校准（对齐真实仓库）

| 原文档设计 | **校准后落地** | 为什么 |
| --- | --- | --- |
| 排放因子 `factor_mg_per_kwh`、排放 `mg` | **因子 `factor_g_per_kwh`（整数克/度）、排放 `emission_g`（整数克）** | 因子量级约 581 g/kWh，本身就是整数，再放大 1000 倍只是徒增溢出风险，见 00 第 4.5 节 |
| 电量 `total_energy_wh` | **`kwh_x100`（度 × 100 的整数）**，与 `t_order.kwh_x100` 一致 | 同上 |
| 时区分桶、`Asia/Shanghai` 转换 | **不做时区转换**。全项目单时区，时间已是本地时间 TEXT，按日聚合直接 `date(settle_time)` | `db-schema.sql` 注释里写明「便于用 `date(x)` 直接按日聚合」，这正是该设计的用途 |
| `carbon_calculation_run` 表（运行范围/输入哈希/状态） | **MVP 简化**：`t_carbon_daily` 上建 `UNIQUE(station_id, stat_date, factor_version, algo_version)`，重算即 `INSERT OR REPLACE`。运行元数据（截止时间、算法版本）作为列存在同一张表 | 一张只记录「跑过一次」的任务表，对课程项目的价值低于它的复杂度 |
| `energy_mix_snapshot` 表（电网/光伏/储能构成） | **MVP 不建表**。项目没有能源构成数据来源，`grid_energy_wh` 即全部充电量；能源构成列为增强项，等 06 的 `t_energy_sample` 有数据后再接 | 建一张永远只有一种来源的表，等于给报告加一个恒为 100% 的字段 |
| 峰平谷切分依赖分时电价 | **依赖模块 05**。05 未完成时降级：按 `t_sys_config` 里的固定时段常量（`carbon_peak_ranges` 等）切分，**页面必须标注「固定时段口径」** | 08 可先开工正是因为它能降级；不标注口径会让人以为是真实分时数据 |
| `data_completeness_bps`（基点） | **整数百分比 0..100**；总量为 0 时返回「不适用」而非 100 | 见 00 第 4.5 节 |
| 报告导出 PDF | **只做 CSV + 可打印 HTML**，PDF 明确不做 | 任务卡已列为非目标 |
| 基础指标由 SQL/C++ 完成，Python 只做图表 | **保留**，且更明确：服务端 `3740` 返回指标；`dataviz/` 的图表读**新增的**快照文件，**不得修改 `ml/export_snapshot.py`**（它的营收/趋势/状态口径已与服务端 2301–2303 对齐过，改动要走 CR） | conventions.md 3.1 有这条对齐记录，改回去等于把已解决的问题再造一遍 |

**口径必须与订单明细对得上**：`total_kwh_x100 = SUM(t_order.kwh_x100 WHERE status = 3)`，`estimated_emission_g = round(kwh_x100 × factor_g_per_kwh / 100)`。报告页与导出文件的数字**必须完全一致**，并在页眉标注「课程项目估算，非认证碳数据」。

**只读原则**：本模块**只读** `t_order` 等业务表，只写自己的 `t_carbon_*` 表（00 第 3 节明文）。

**命令字登记表**：

| 命令字 | 常量名 | 方向 | `data` |
| --- | --- | --- | --- |
| 3740 | `CMD_EXT_CARBON_METRIC` | 管理端 | `{stationId, dateFrom, dateTo}` → `{list[], factorVersion, algoVersion, cutoffTime, completeness, disclaimer}` |
| 3741 | `CMD_EXT_FACTOR_LIST` | 管理端 | `{}` → 因子版本列表 |
| 3742 | `CMD_EXT_FACTOR_SET` | 管理端（需权限） | `{region, effectFrom, factorGPerKwh, source, reqId}` |
| 3743 | `CMD_EXT_REPORT_GEN` | 管理端 | `{scope, dateFrom, dateTo, reqId}` → `{reportId, version}` |

**错误码登记表**：`6701 ERR_CARBON_NO_FACTOR`（该时段无有效因子）、`6702 ERR_CARBON_FACTOR_OVERLAP`（因子生效区间重叠）、`6703 ERR_CARBON_REPORT_STALE`（源数据已变，需重算）。

### 5.1 架构

以下名称表示职责，认领人必须先映射到仓库真实结构（见第 5.0 节），不要求创建同名目录：

- `CarbonSourceReader`：只读获取已结算订单、可选表计区间和能源构成。
- `TimeBucketSplitter`：按统一时区把会话切分到自然日、因子区间和峰平谷区间。
- `EmissionFactorRepository`：校验地区、生效时间、单位、来源和版本，禁止重叠生效。
- `CarbonCalculator`：无数据库副作用的纯计算组件，使用整数和固定舍入规则。
- `CarbonAggregationService`：幂等运行、锁定统计范围、保存聚合和输入摘要。
- `EnergyReportService`：预览、版本化生成、标记 `STALE` 和导出。
- `CarbonQueryService`：向 Qt 管理端和 Web 返回指标、质量、口径和版本。

统计任务不应持有长事务读取全库。先确定 `data_cutoff_at`，再按该截止时间分页读取并计算；写入聚合时使用短事务。基础指标应能由 SQL/C++ 完成，Python 只可用于可选图表或导出。

### 5.2 数据

| 实体 | 必要字段 |
|---|---|
| `emission_factor` | 因子 ID、地区、能源来源、`effective_from/to`、`factor_mg_per_kwh`、来源说明/链接、版本、启用状态 |
| `energy_mix_snapshot` | 站点、时间窗、电网/光伏/储能/未知来源 Wh、质量标记、来源 |
| `carbon_calculation_run` | 范围、截止时间、时区、因子集合、算法版本、状态、输入摘要/哈希、错误信息 |
| `carbon_metric_daily` | 运行、站点、日期、总 Wh、峰/平/谷/未分配 Wh、电网 Wh、估算排放 mg、强度、完整度基点 |
| `energy_report` | 报告 ID、范围、版本、运行 ID、状态、口径快照、生成时间、输出位置/内容摘要 |

建议唯一键至少覆盖“站点 + 日期 + 数据截止时间 + 因子集合版本 + 算法版本”。若仓库已有通用任务表、文件表或统计表，应优先复用，不重复造表。

### 5.3 指标和算法

基础指标：

- `total_energy_wh`：纳入范围内 `PAID` 订单最终充电量之和。
- `peak/flat/valley/unallocated_energy_wh`：按分时区间切分，四项之和必须等于总充电量。
- `grid_energy_wh`：有能源构成时使用电网分项；无构成时使用文档化的购电量代理。
- `estimated_emission_mg`：按因子区间计算 `round_half_up(energy_wh * factor_mg_per_kwh / 1000)`，使用足够宽的整数中间值并在最终粒度舍入。
- `emission_intensity_mg_per_kwh`：显示指标可在查询层计算，持久化时使用整数或定点精度并处理分母为 0。
- `data_completeness_bps`：有足够来源、时间和因子支持的电量占总电量的基点比例；总量为 0 时返回明确的“不适用”，不伪装为 100%。
- `estimated_energy_bps`：使用 `UNIFORM_ESTIMATE` 的电量占比，用于页面提示。

时间统一按项目配置时区（默认业务演示可为 `Asia/Shanghai`）分桶，数据库时间仍保持统一格式。跨午夜、跨峰谷和跨因子生效时间的订单必须切片后再计算。

### 5.4 服务接口

沿用项目统一 Socket/服务接口风格，建议增加或复用：

- `CARBON_METRIC_QUERY`
- `EMISSION_FACTOR_LIST / EMISSION_FACTOR_SET`
- `REPORT_PREVIEW / REPORT_GENERATE / REPORT_STATUS / REPORT_EXPORT`

查询响应必须同时返回 `dataCutoffAt`、时区、因子版本、算法版本、完整度、估算占比和免责声明。导出文件中的数值与同一报告版本的页面数值必须完全一致。

### 5.5 UI 与导出

- 管理端：日期/站点筛选、因子版本、指标卡、峰平谷构成、排放趋势、数据完整度、口径说明、预览和导出。
- Web/ECharts：用电趋势、估算排放趋势、分时占比、站点强度对比和缺失/估算比例。
- 用户端为可选增强，只展示个人累计充电量和“估算贡献”说明；MVP 不依赖它。

导出首选 CSV 和可打印 HTML。只有仓库已有稳定 PDF 能力且不显著扩大范围时才增加 PDF；所有导出页眉必须包含“课程项目估算，非认证碳数据”。

## 7 测试矩阵

| 层级 | 场景 | 关键断言 |
|---|---|---|
| 单元 | g/kWh 对应的整数因子换算、半舍入、超大值 | mgCO2e 结果正确，无溢出或浮点累计误差 |
| 单元 | 零电量、负电量、缺失最终电量 | 零值处理明确；非法值拒绝并记录，不进入聚合 |
| 单元 | 跨午夜、跨峰/平/谷边界 | 切片无重叠无遗漏；各分项和等于订单 Wh |
| 单元 | 因子起止边界和重叠因子 | 左闭右开选择正确；重叠配置被拒绝 |
| 单元 | 只有订单总量的均匀分摊 | 余数稳定分配；标记 `UNIFORM_ESTIMATE` 并计入估算占比 |
| 集成 | `PAID` 与其他状态混合 | 只计入已结算订单，每个订单一次 |
| 集成 | 同一范围重复运行 | 幂等键生效，无重复行，输入相同结果一致 |
| 集成 | 缺失因子、缺失起止时间、缺失能源构成 | 完整度降低、警告可见，不填充伪造实测值 |
| 集成 | 修改因子生效日期 | 旧报告 `STALE`，新报告使用新因子且保留旧版 |
| 集成 | 补录迟到 `PAID` 订单或纠正最终 Wh | 仅受影响范围过期并重算，其他报告不变 |
| 集成 | 计费电量与站点能耗不同 | 两类指标分开展示，不被强制对齐 |
| 并发 | 同一范围同时生成两次 | 只有一个运行成为执行者或两个请求复用同一结果 |
| 恢复 | 生成中服务重启/导出失败 | 任务进入可诊断状态并可安全重试，不产生 READY 空报告 |
| 端到端 | 手算数据生成页面与 CSV/HTML | 页面、数据库、导出和预期结果完全一致 |
| 边界 | 空日期范围、无订单站点、非法时区/日期 | 返回明确空结果或校验错误，服务不崩溃 |

## 8 Definition of Done

- [ ] 一组固定订单能够生成可手算复核的日/月总 Wh、峰平谷分布和估算电网间接排放。
- [ ] 所有计算只纳入 `PAID` 订单；报表代码没有修改订单、钱包、支付、设备遥测或正式营收的路径。
- [ ] 因子、单位、时区、算法版本、数据截止时间、舍入和质量方法均能从结果追溯。
- [ ] 能量和排放关键值使用整数/定点算法，跨区间切片守恒且没有浮点累计误差。
- [ ] 缺失数据会降低完整度并显示警告；页面不会把估算数据显示为实测。
- [ ] 报告固定标注“估算、非认证、不可用于碳交易或监管申报”。
- [ ] 迟到数据和因子修订使旧报告 `STALE`，新版本重算且旧版本仍可查询。
- [ ] 页面、聚合表和同一版本导出文件中的数字一致。
- [ ] 测试矩阵核心场景通过；失败或未执行项有具体原因和风险说明。
- [ ] 运行说明包含演示因子来源说明、固定测试数据、重算方法、导出位置和非目标。

## 9 风险与降级方案

| 风险 | 识别信号 | 降级方案 |
|---|---|---|
| “减排”口径不成立 | 缺少燃油车基准、车辆能效或能源边界 | 模块和 UI 改称“排放估算”；只展示购电间接排放和用电结构 |
| 表计区间缺失 | 只有订单总 Wh | 总量照常统计；分时按时长估算并显著标注，或直接列为未分配 |
| 排放因子来源不可靠 | 无明确地区、日期或来源 | 使用显式“演示因子”并禁止对外宣称；允许管理员配置版本，报告展示来源 |
| PDF 工作量过大 | 字体、分页和跨平台渲染反复失败 | MVP 交付 CSV + 可打印 HTML，不阻塞核心指标 |
| 数据修订机制复杂 | 难以实时追踪所有迟到事件 | 每日定时按受影响日期重算；旧报告仍按截止时间保持不可变 |
| SQLite 聚合耗时 | 长范围统计影响在线请求 | 日级增量聚合、分页读取、短事务；月报从日指标汇总 |
| 能源构成不可用 | 没有光伏/储能来源追踪 | 基础版只报告购电量代理及假设，不输出“绿电占比” |
