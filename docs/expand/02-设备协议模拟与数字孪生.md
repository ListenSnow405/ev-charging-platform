# 02 · 设备协议模拟与数字孪生

## 1 文档用途

本文是扩展模块 02 的任务规格。技术底座、命令字分段、单位口径、接缝规则见 [00-扩展功能模块实施路径推荐.md](00-扩展功能模块实施路径推荐.md) 第 4、5 节；**凡本文第 5 节与 00 第 4 节冲突，以 00 为准**。

**本模块与 R0-2 是同一条链的两段**：R0-2（`9001–9004` 服务端 handler）属于核心欠账，不计入本模块工作量；本模块只做**其上的孪生能力**——连接世代、遥测存储、命令下发与结果关联、故障注入、场景脚本、管理端孪生视图。

本模块是 03 告警工单、06 能源管理、10 V2G 的共同前置，建议由 **L1** 认领：设备段协议、`tools/pile-simulator/`、推送通道（B2）本就是他的目录。

## 3 业务流与数据流

### 3.1 建连与心跳

```text
模拟器建立 Socket
  -> 服务端 DeviceGateway 读取长度帧并校验大小
  -> DEVICE_HELLO / DEVICE_AUTH
  -> DeviceSessionService 建立 connectionGeneration
  -> 模拟器周期发送 HEARTBEAT / STATUS_REPORT
  -> 服务端更新连接记录与 device_twin_snapshot
  -> 超过阈值未收到心跳时标记设备 OFFLINE，并记录事件
```

新连接成功后，旧连接世代立即失效。旧连接后续上报只能得到明确错误，不能覆盖新连接的孪生快照。

### 3.2 开始充电

```text
用户端请求开始充电
  -> 订单服务校验订单为 RESERVED、用户无待结算限制冲突、电桩为 RESERVED
  -> 服务端事务写入命令意图/发件箱
  -> DeviceGateway 下发 START_CHARGE
  -> 模拟器仅执行设备侧模拟并返回 COMMAND_ACK / COMMAND_RESULT
  -> 服务端校验 messageId、订单、电桩、连接世代和命令结果
  -> 业务事务推进订单为 CHARGING、电桩为 CHARGING
  -> 用户端从服务端读取权威状态
```

模拟器返回成功并不等于订单一定成功；只有服务端事务提交后，订单状态才发生变化。

### 3.3 遥测、停止与计费输入

```text
模拟器按固定周期生成电压/电流/功率/累计电量
  -> TELEMETRY_REPORT
  -> 服务端去重、校验单位与单调性
  -> 写入遥测明细并更新数字孪生
  -> 用户端展示服务端返回的功率、电量和预计费用

用户请求停止
  -> 订单服务写入 STOP_CHARGE 命令意图
  -> 模拟器停止累计并回传最终电表读数
  -> 服务端校验最终读数
  -> 事务推进订单至 PENDING_PAYMENT，并保存计费所需最终电量
```

用户端可以显示“预计费用”，但不能把本地定时累计值写回订单，也不能据此扣减钱包。

## 4 状态与不可破坏约束

### 4.1 状态定义

- 电桩继续复用 `t_pile.status` 的**三态**（0 在用 / 1 闲置 / 2 故障）与正交的 `t_pile.online`，不得增加同义状态；详见 [00 第 4.5.1 节状态命名映射](00-扩展功能模块实施路径推荐.md)。
- 订单继续复用 `RESERVED -> CHARGING -> PENDING_PAYMENT -> PAID`；取消进入 `CANCELLED`。
- 设备命令状态：`QUEUED -> SENT -> ACKED -> EXECUTING -> SUCCEEDED`，异常终态为 `FAILED / TIMEOUT / CANCELLED`。
- 连接状态建议只表达 `ONLINE / OFFLINE`，并由 `connectionGeneration` 区分连接世代。

### 4.2 不变量

1. 同一设备同一时刻最多存在一个有效连接世代。
2. 同一电桩同一时刻最多服务一个有效订单。
3. 只有权威订单状态为 `RESERVED` 时，服务端才可生成开始命令；只有 `CHARGING` 时才可生成停止命令。
4. 设备 ACK 只表示收到命令，不能推进订单；必须收到匹配的成功结果并完成业务事务。
5. `messageId + deviceId` 必须幂等；重复消息返回首次处理结果，不重复执行。
6. 遥测乱序不得让累计电量倒退；异常跳变要记录质量标记并拒绝作为最终计费读数。
7. 心跳超时只能使设备进入 `OFFLINE` 并触发后续异常处理，不能把订单擅自改为 `PAID`、`CANCELLED` 或扣减钱包。
8. 模拟器故障、重连和服务重启后，不得出现重复开始、重复停止或重复计费。

## 5 建议实现设计

### 5.0 技术路线校准（对齐真实仓库）

| 原文档设计 | **校准后落地** | 为什么 |
| --- | --- | --- |
| 设备自定信封 `{version, type, messageId, deviceId, sequence, timestamp, connectionGeneration, payload}` | **沿用已冻结信封 `{cmd, seq, token, data}`**；`pileCode`、`seqNo` 放 `data`；`connectionGeneration` 由服务端维护在 `t_dev_conn`，**不进报文** | 协议 §2/§3 已冻结；第二套信封意味着 `FrameCodec` 之外再写一套解析，直接违反 CLAUDE.md 硬性规则 1 |
| `DEVICE_HELLO` / `DEVICE_AUTH` / `HEARTBEAT` 等动作名 | **映射为设备段数字命令字**：注册 9001、上报 9002、重启 9003、心跳 9004 已冻结；新增见下表 9005–9049 | 同上 |
| 设备凭证摘要鉴权 | **MVP：`pileCode` 存在于 `t_pile.pile_code` 即认**，设备连接的 handler 按 `needAuth=false` 注册。设备凭证列为增强项 | 与"实训环境不做 TLS"同一类取舍，需写进设计文档；引入设备密钥要动冻结的 `t_pile` |

| `device_event` 表 | **复用 `t_pile_log`**（`event` 已定义 0 上线 / 1 离线 / 2 状态变更 / 3 远程重启 / 4 故障上报） | 已冻结且大屏与 ML 已在取数 |

| 能量 Wh、功率 W、UTC 时间 | **`kwh_x100` 整数 / `power_kw` REAL / 本地时间 TEXT** | 见 00 第 4.5 节勘误表；与 `t_order.kwh_x100`、`t_pile.power` 一致 |
| 每台设备一个线程 | **模拟器单进程 + `QTimer` 驱动多设备**（原文已如此要求，保留）；服务端侧沿用一连接一线程的既有模型 | `TcpServer` 的池大小即最大并发连接数，模拟 50 台设备会吃满线程池——**演示规模建议 ≤ 6 台**，或先调大 `config/app.ini` 的 `pool_size` |
| 设备级串行处理 | 天然满足：一条设备连接由**一个**工作线程从头服务到断开 | 现有模型的副产品，不需要额外加锁 |

### 5.1 架构

先检查仓库现有分层和命名，再把以下职责映射到实际目录，禁止为了匹配本文而臆造路径：

- `DeviceGateway`：Socket 连接、长度帧拆包、帧大小限制、鉴权、发送队列和断连。
- `DeviceSessionService`：连接世代、设备级串行处理、心跳超时和合法状态校验。
- `DeviceCommandService`：命令意图、发件箱、重试、超时、ACK/结果关联。
- `DeviceTelemetryService`：遥测校验、批量持久化、最终表读数立即落库。
- `DeviceTwinQueryService`：返回最近可信状态、指标、更新时间和数据新鲜度。
- `BusinessOrderService`：唯一有权推进订单、更新电桩权威状态及形成计费输入的组件。
- `DeviceSimulator`：不连接业务数据库的独立进程；用一个事件循环和 `QTimer` 模拟多台设备，不为每台设备常驻一个线程。

同一设备的消息按 `deviceId` 串行处理；不同设备可以并发。SQLite 场景下采用短事务和有界写队列，避免遥测写入长期占锁。

### 5.2 数据

在不重复仓库已有表的前提下，建议具备以下逻辑实体：

| 实体 | 必要字段 |
|---|---|
| `device_registry` | `device_id`、所属站点/电桩、协议版本、能力集合、凭证摘要、启用状态 |
| `device_connection` | `device_id`、`connection_generation`、上线时间、最后心跳、离线时间、断开原因 |
| `device_telemetry` | `device_id`、关联订单、采样时间、序号、电压/电流/功率、累计电量、温度、质量标记 |
| `device_event` | 事件类型、设备、连接世代、时间、前后状态、原因、原始消息编号 |
| `device_command` | 命令编号、类型、设备、关联订单、请求参数、状态、尝试次数、超时、结果 |
| `device_twin_snapshot` | 最近可信状态、最近指标、连接世代、更新时间、最后序号、数据新鲜度 |
| `device_inbox` | `device_id`、`message_id`、处理结果摘要、首次处理时间；联合唯一键用于去重 |

**单位口径以第 5.0 节与 [00 第 4.5 节](00-扩展功能模块实施路径推荐.md)为准**：金额 `qint64` 整数分、功率 kW（REAL）、电量 `kwh_x100`、时间 `TEXT 'yyyy-MM-dd HH:mm:ss'` 本地时间。扩展建表脚本与演示种子必须幂等，可重复执行。

### 5.3 协议

沿用项目统一的“4 字节大端长度头 + UTF-8 JSON”。所有设备消息至少包含：

```json
{
  "version": "1.0",
  "type": "HEARTBEAT",
  "messageId": "唯一请求号",
  "deviceId": "设备编号",
  "sequence": 12,
  "timestamp": "带时区时间",
  "connectionGeneration": 3,
  "payload": {}
}
```

MVP 消息集合限定为：

- 建连：`DEVICE_HELLO`、`DEVICE_AUTH`、`HEARTBEAT`。
- 上报：`STATUS_REPORT`、`TELEMETRY_REPORT`、`FAULT_REPORT`、`FAULT_CLEAR`。
- 命令：`START_CHARGE`、`STOP_CHARGE`、`REMOTE_RESTART`。
- 应答：`COMMAND_ACK`、`COMMAND_RESULT`、统一错误响应。

`SET_POWER_LIMIT` 可在能源管理模块实施时补充。协议必须定义最大帧长、字段类型、单位、超时、重试、序号溢出和错误码；未知字段可忽略，未知消息类型必须明确拒绝。

### 5.4 模拟规则

- 固定随机种子，保证演示结果可复现。
- 每个场景由配置描述：初始状态、额定功率、遥测周期、故障时刻、断线时刻和恢复时刻。
- 累计电量按时间积分并保持单调；停止时发送一次带 `final=true` 的最终读数。
- 状态变化由命令或脚本驱动，不允许模拟器绕过命令直接推进订单。
- 首版提供四个场景：正常充电、过温故障、通信中断、断线重连。

### 5.5 UI

MVP 管理端只需提供设备列表/拓扑、在线状态、最后心跳、最新遥测、命令时间线、故障注入和重连按钮。用户端充电页展示服务端返回的当前功率、累计电量、数据更新时间和预计费用。若 Web 大屏已存在，可追加在线率、心跳延迟和命令成功率；它不是 MVP 阻塞项。

## 6 顺序实施步骤

| 步骤 | 实施内容 | 本步产出 | 完成验证 |
|---|---|---|---|
| 1 | 盘点仓库中的 Socket、状态枚举、订单服务、扩展建表脚本和测试入口，冻结协议单位与边界 | 一份短计划、现状映射和协议字段表 | 能指出复用位置、缺口及不会修改的范围；无臆造目录 |
| 2 | 增加设备表/索引/约束和可重复种子数据 | 扩展建表脚本、演示设备和回滚/重建说明 | 连续初始化两次结果一致；联合唯一键和外键生效 |
| 3 | 实现长度帧解析、帧大小限制、注册、鉴权和单连接世代 | `DeviceGateway` 最小链路 | 正常建连成功；非法长度、错误凭证和旧世代均被拒绝且服务不崩溃 |
| 4 | 实现心跳、离线检测、状态上报和数字孪生查询 | 在线/离线事件和最新快照接口 | 停止心跳后按阈值转 `OFFLINE`；重连后旧连接无法覆盖快照 |
| 5 | 实现独立单设备模拟器及固定种子遥测 | 可脚本启动的模拟器 | 相同配置运行两次得到一致事件序列；累计电量单调 |
| 6 | 实现命令表、发件箱、ACK/结果、超时与幂等 | 命令闭环 | 重发同一命令不会重复执行；超时有明确终态；服务重启可恢复未终结命令 |
| 7 | 把 `START_CHARGE` 接入订单服务 | 预约到充电中的端到端链路 | 只有合法预约能进入 `CHARGING`；设备失败时订单保持原合法状态 |
| 8 | 把遥测与 `STOP_CHARGE` 接入最终电量和待结算流程 | 充电、停止、计费输入闭环 | 最终读数只接收一次；订单进入 `PENDING_PAYMENT`，钱包未被模拟器直接改变 |
| 9 | 增加故障注入、掉线重连和单进程多设备 | 可重复异常演示脚本 | 一台掉线不影响其他设备；故障/恢复均有事件；无重复订单 |
| 10 | 补最小管理端/用户端展示、自动化测试和运行说明 | 可验收的 MVP | 按演示脚本从冷启动完整跑通，测试通过，日志可关联 `messageId/deviceId/orderId` |

每一步都应保持可构建。若某一步需要跨越尚未实现的前置模块，先提供接口适配器或只读假数据源，不要顺手开发另一个完整扩展模块。

## 7 测试矩阵

| 层级 | 场景 | 关键断言 |
|---|---|---|
| 单元 | 长度帧半包、粘包、零长度、超长帧、非法 UTF-8/JSON | 合法帧正确拆分；非法帧返回错误并安全断开 |
| 单元 | 重复 `messageId` | 只执行一次，后续返回首次结果 |
| 单元 | 遥测重复、乱序、累计电量倒退、异常跳变 | 不污染可信快照和最终计费读数；质量标记可查询 |
| 单元 | 电桩和订单非法状态迁移 | 被业务服务拒绝，数据库无部分提交 |
| 集成 | 鉴权成功/失败、同设备第二连接 | 只有最新连接世代有效，凭证不写入日志明文 |
| 集成 | 正常开始—遥测—停止 | `RESERVED -> CHARGING -> PENDING_PAYMENT` 唯一推进，最终 Wh 一致 |
| 集成 | ACK 成功但结果失败/超时 | 订单不误推进；命令进入明确异常终态 |
| 集成 | 停止命令重复发送和最终读数重复上报 | 订单、计费输入和事件均不重复 |
| 集成 | 充电中断网、旧连接迟到消息、重连 | 设备离线；迟到消息无效；重连恢复后无重复开始 |
| 集成 | 服务在命令发送后重启 | 发件箱恢复，命令最终收敛到一个终态 |
| 并发 | 多设备同时心跳和遥测 | 设备间互不阻塞；同设备事件顺序稳定；SQLite 无长期锁死 |
| 端到端 | 用户预约、设备执行、停止、待结算 | UI、服务端、数据库和日志对同一订单显示一致 |
| 安全 | 伪造设备、未知消息、超大 payload、高频消息 | 请求被限制/拒绝，服务稳定，敏感信息不泄漏 |

## 8 Definition of Done

- [ ] 代码、协议和运行说明使用“项目自定义简化协议”，没有 OCPP 兼容/认证误导。
- [ ] 从全新数据库可重复初始化演示设备并启动服务端、模拟器和所需客户端。
- [ ] 一台设备能够完成鉴权、心跳、状态、遥测、开始和停止命令闭环。
- [ ] 最终充电量来自设备链路并由服务端校验，用户端不自行写入权威电量。
- [ ] 模拟器和模型没有订单表、钱包表的直接写权限或代码路径。
- [ ] 重复、乱序、超时、掉线、重连和服务重启不会产生重复订单、重复计费或非法状态。
- [ ] 日志能够通过 `messageId`、`deviceId`、`commandId` 和 `orderId` 定位一次完整交互，且不记录明文凭证。
- [ ] 自动化测试覆盖测试矩阵中的核心项并全部通过；失败测试及原因已如实报告。
- [ ] MVP 演示脚本可在一套固定种子数据上重复运行，关键结果一致。
- [ ] 未完成的增强项有清晰 TODO/接口，不伪装为已实现能力。

## 9 风险与降级方案

| 风险 | 识别信号 | 降级方案 |
|---|---|---|
| 协议范围膨胀 | 不断增加 OCPP 消息、认证、固件等需求 | 锁定 MVP 消息集合，只保留注册、鉴权、心跳、状态、遥测、开始、停止和重启 |
| SQLite 写竞争 | 遥测时出现 `database is locked` 或请求延迟陡升 | 遥测 5～10 秒一次、批量短事务；关键状态和最终读数仍立即写入；历史数据按分钟聚合 |
| UI 消耗时间过多 | 协议链路未通但已投入复杂拓扑/动画 | 保留表格和时间线，故障注入用简单按钮或配置文件 |
| 命令恢复过于复杂 | 重启后难以判断设备是否执行 | 先实现“查询/重发并幂等收敛”；无法确认时标记 `TIMEOUT` 并要求人工重试，绝不推测订单成功 |
| 多设备不稳定 | 线程数、连接数或时序问题频发 | 保留单进程事件循环，先验收 1～3 台设备，不做高并发承诺 |
| 前置订单服务边界不清 | UI 或模拟器仍能直接更新订单 | 暂停接入，先把订单迁移集中到服务端；在此之前只演示设备连接和遥测 |
