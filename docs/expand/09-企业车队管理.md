>

> **只有在第三批次（00 第 7 节）仍有明显余量时，才从 09 / 10 中二选一。** 若确实认领，必须先经 PM 与 L2 同意并记入 [CLAIM.md](CLAIM.md)。

## 3 业务流程

### 3.1 企业开通与维护

1. 平台管理员创建企业，填写展示名称和内部编号，并绑定一个已存在的手机号用户为企业负责人。
2. 企业负责人或车队管理员从已有用户中添加成员，分配车队角色；首版不发送邀请，也不创建重复用户账号。
3. 车队管理员新增车辆并绑定一个或多个企业司机。车辆仅保存演示所需编号、车牌掩码/别名和状态，不保存真实 VIN 或位置。
4. 平台管理员为企业钱包执行模拟充值，生成完整的钱包流水和审计记录。
5. 车队管理员设置默认消费策略：单次上限、月度上限；站点、时段、成本中心等限制留待后续。

### 3.2 企业付款预约与充电

1. 已登录司机在预约页面主动选择“企业支付”、企业和车辆。客户端可展示候选项，但无权决定最终授权结果。
2. 服务端根据登录用户重新查询有效企业成员关系、企业状态、车辆状态、司机绑定、默认策略、企业钱包可用余额及用户未结算订单。
3. 服务端计算预估金额，并在同一业务事务中创建订单、不可变 `fleet_order_context` 和 `budget_hold`。并发请求必须通过条件更新/约束阻止额度和余额被重复占用。
4. 订单进入 `CHARGING` 后，企业、车辆、付款钱包和策略快照不得静默变更；企业被冻结可以阻止新订单，但不得丢失已有订单的结算责任。
5. 预约取消或超时后释放预占。任何释放操作都必须幂等，不能把同一笔额度释放两次。

### 3.3 结算与余额不足

1. 订单结束后仍按核心流程进入 `PENDING_PAYMENT`，最终金额由现有计费服务计算。
2. 结算服务读取订单企业上下文和有效预占，校验实际金额是否超出单次/月度上限，并计算超出预占的增量。
3. 在一个事务内扣减企业钱包、写流水、消费/释放预占、记录企业消费并将订单推进为 `PAID`。
4. 若余额或额度不足，订单保持 `PENDING_PAYMENT`，企业管理员充值或调整允许的额度后使用同一幂等语义重试。系统不得未经用户明确操作改扣个人钱包。
5. 无论由个人还是企业付款，用户存在未结算订单时都继续触发原有“禁止发起新充电”规则。

### 3.4 月度账单

1. 企业管理员选择企业和账期，请求服务端从该企业已支付订单及钱包流水生成账单。
2. 账单行保存订单、车辆、司机、金额和支付时间的快照；同一企业同一账期重复生成返回现有账单或创建新版本，不得重复记账。
3. 企业管理员核对后确认账单。账单只做汇总与对账，不反向扣款或修改历史订单。

## 4 状态、金额与不可破坏约束

### 4.1 状态定义

- 核心订单继续使用 `RESERVED`、`CHARGING`、`PENDING_PAYMENT`、`PAID`、`CANCELLED`，不得新增 `FLEET_PAID`、`CORPORATE_PENDING` 等不兼容值。
- 企业状态：`ACTIVE <-> FROZEN`，以及终态 `CLOSED`。关闭前必须不存在有效订单、待结算订单和活动预占。
- 成员状态：首版使用 `ACTIVE <-> SUSPENDED`，并可进入终态 `LEFT`。若未来增加邀请，再扩展 `INVITED -> ACTIVE`，首版不要制造虚假邀请流程。
- 车辆状态：`ACTIVE -> DISABLED -> ACTIVE`，以及终态 `RETIRED`。非 `ACTIVE` 车辆不能创建新企业订单。
- 预算预占状态：`ACTIVE -> CONSUMED` 或 `ACTIVE -> RELEASED`；预约自然失效可记为 `EXPIRED`。充电中或待结算订单的预占不得自动过期。
- 账单状态：`GENERATING -> GENERATED -> CONFIRMED`；生成失败应回滚未完成账单，或使用模块内部 `FAILED` 并允许幂等重试。

所有迁移由服务端集中校验。冻结企业、暂停成员或禁用车辆只影响后续授权，不允许通过直接修改历史上下文改变既有订单。

### 4.2 金额与额度规则

- 企业余额、充值、预占、消费、额度和账单金额统一使用 64 位整数分，字段建议以 `_cents` 结尾；禁止使用浮点数结算。
- 可用余额按服务端权威数据计算：`钱包余额 - 活动预占总额`。月度可用额度按“账期内已支付企业消费 + 活动预占”计算。
- 预估金额由服务端计价能力或明确的保守规则生成，客户端提交的预估额和剩余额度均不可信。
- 结算金额低于预占时释放差额；高于预占时原子校验并占用增量。余额不足时不得形成负余额。
- 账单总额必须等于其账单行金额之和，并能与相应已支付订单和企业钱包消费流水对账。

### 4.3 不可破坏约束

- 请求中的 `organizationId`、`vehicleId`、`payerType` 和角色都只是候选输入，服务端必须基于当前登录用户重新授权。
- 每个订单最多一个企业上下文和一个最终付款钱包；开始充电后不得静默从企业付款切换为个人付款。
- 企业上下文必须保存企业、成员、司机、车辆、成本归属、付款钱包和消费策略快照，历史记录不能依赖后来会变化的成员关系。
- 一个成员、车辆或企业被停用后，历史订单与账单仍可读；禁止物理删除有业务引用的数据。
- 创建企业订单与预算预占、取消订单与释放预占、支付与消费预占必须分别保持原子和幂等。
- 企业钱包不允许透支，所有余额变更必须有流水和审计；UI 和企业模块不得直接更新余额列。
- 任何组织级列表、详情、统计和账单都必须按服务端授权的组织范围隔离，不能只依赖前端筛选。
- 功能开关关闭或企业模块故障时，个人用户的登录、预约、充电和个人钱包结算必须保持原行为。

## 5 建议架构、数据、协议与 UI

### 5.0 技术路线校准（对齐真实仓库）

| 原文档设计 | **校准后落地** | 为什么 |
| --- | --- | --- |
| `wallet_account` 扩展为 `owner_type = USER / ORGANIZATION` | **禁止改造个人钱包。** `t_user.balance` 与 `t_wallet_tx` 已冻结且被 1005/1006/1205/统计/大屏多处消费。企业钱包独立建 `t_org_wallet` + `t_org_wallet_tx` | 抽象通用所有者模型要重写全部既有钱包代码，是本模块最大的风险源 |
| `fleet_order_context` 表（订单唯一） | **保留，且是首选方案**：`t_fleet_order_ctx`（`order_id UNIQUE, org_id, member_user_id, vehicle_id, payer_type, policy_json, create_time`）旁挂。**不给 `t_order` 加 `payer_type` / `org_id` 列** | 旁挂对核心表零改动；加列要走 CR 且影响所有既有查询 |
| 企业付款在既有结算里分支 | **这是本模块唯一无法回避的核心改动。** 落地方式：由 **L2** 在 1205 结算入口加一处「查 `t_fleet_order_ctx`，有企业上下文则转企业结算」的分派，**由 L2 落笔而非认领人**；认领人只提供企业侧的结算实现 | 00 第 5.2 节：改不动的接缝必须停手上报，不能由认领人直接改核心 |
| 预算预占 `budget_hold` | 保留为 `t_fleet_budget_hold`（`order_id UNIQUE, org_id, hold_fen, status, deadline, version`）；预占释放挂 B1 定时任务 | 与模块 04 的 hold 是同一套思路 |
| 「余额不足时订单保持待结算」 | 保留。**且绝不能自动改扣个人钱包**——必须由用户显式选择且只能在开始充电前 | 原文已强调，是本模块最容易被 agent 写错的地方 |
| 金额 | 一律 `qint64` 整数分；额度（单次/月度）同样是整数分 | 见 00 第 4.5 节 |
| UUID / 业务编号 | `INTEGER PRIMARY KEY AUTOINCREMENT` + `org_no TEXT UNIQUE`，与 `t_order(order_id, order_no)` 一致 | 同上 |
| 新增「余额不足 / 版本冲突 / 未结算」错误码 | 复用 `2004` / `4002`；企业侧额度不足才用新码 | 见 00 第 4.3 节 |

**命令字段**：`3800–3839` 用户端（可用企业/车辆查询、企业付款预约、企业订单查询），`3840–3879` 管理端（企业增删改、成员、车辆、充值、策略、账单）。

**错误码登记表**：`6801 ERR_ORG_FROZEN`、`6802 ERR_ORG_MEMBER`（非成员/已停用）、`6803 ERR_VEHICLE_UNAVAILABLE`、`6804 ERR_QUOTA_ONCE`（单次额度不足）、`6805 ERR_QUOTA_MONTH`（月度额度不足）、`6806 ERR_ORG_BALANCE`（企业可用余额不足）、`6807 ERR_ORG_VERSION`。

**建表脚本 `docs/db-schema-ext-09.sql`**：`t_org`、`t_org_member`（`UNIQUE(org_id, user_id)`）、`t_fleet_vehicle`、`t_fleet_driver_bind`、`t_org_wallet`、`t_org_wallet_tx`、`t_fleet_policy`、`t_fleet_order_ctx`、`t_fleet_budget_hold`、`t_fleet_statement`（`UNIQUE(org_id, period, version)`）、`t_fleet_statement_line`（`UNIQUE(statement_id, order_id)`）。

**组织隔离必须服务端强制**：所有查询从会话身份推导可见的 `org_id` 集合，**不接受客户端传入的 `orgId` 作为可信输入**；失败原因不得泄露其他企业的数据。

### 5.1 服务端架构

根据现有工程分层映射下列职责，不要求机械创建同名文件：

- `OrganizationService`：企业生命周期、成员与角色、组织范围查询。
- `FleetVehicleService`：车辆状态、司机绑定和企业归属。
- `FleetAuthorizationService`：基于登录用户校验企业、成员、车辆、付款方和策略，并返回明确拒绝原因。
- `FleetWalletService`：复用或扩展统一钱包，处理企业充值、可用余额、预占和流水。
- `FleetSettlementCoordinator`：把企业上下文、预算预占、现有计费和核心订单结算组织进事务。
- `FleetStatementService`：从已支付订单/流水生成不可变账单行和对账摘要。

建议调用链：`Qt/Web -> Socket 网关 -> 用户鉴权 -> 组织范围授权 -> 业务服务 -> Repository -> SQLite`。企业功能通过服务端能力或功能开关隔离，不要把企业逻辑散落到每一个 UI 页面。

### 5.2 数据模型

按仓库现有命名、主键和迁移规范落地，至少需要：

| 建议实体 | 关键字段或约束 |
| --- | --- |
| `organization` | 内部编号、名称、状态、创建时间；内部编号唯一 |
| `organization_member` | 企业、用户、角色、状态、加入/离开时间；企业 + 用户唯一 |
| `vehicle` | 企业、展示编号/车牌掩码、状态；企业内展示编号唯一 |
| `vehicle_driver_binding` | 车辆、成员、状态/有效期；成员必须属于同一企业 |
| `wallet_account` 扩展 | `owner_type=USER/ORGANIZATION`、`owner_id`、余额分、版本号；所有者组合唯一 |
| `spending_policy` | 企业、单次上限分、月度上限分、状态、版本号 |
| `policy_assignment` | 策略与企业/成员的关联；MVP 可只启用一个企业默认策略 |
| `fleet_order_context` | 订单唯一、企业、成员、车辆、付款钱包、策略快照、创建时间 |
| `budget_hold` | 订单唯一、企业钱包、预占分、状态、到期时间、版本号 |
| `fleet_statement` | 企业、账期、版本、状态、合计分、生成/确认时间；企业 + 账期 + 版本唯一 |
| `fleet_statement_line` | 账单、订单、车辆/司机快照、金额分、支付时间；账单 + 订单唯一 |

若现有钱包模型难以直接扩展，应优先抽象通用“所有者类型 + 所有者 ID”而不是复制企业钱包业务逻辑；但不得以大规模无关重构为代价。SQLite 外键、唯一约束、查询索引和条件更新必须与服务层校验共同落地。

### 5.3 Socket 协议

逻辑动作应适配仓库现有 action 命名和消息 envelope，至少覆盖：

| 方向 | 逻辑动作 | 核心输入/输出 |
| --- | --- | --- |
| 平台管理端 | 企业创建/冻结/解冻/查询 | 企业资料、状态和分页；返回审计关联信息 |
| 企业管理端 | 成员添加/停用、车辆增改/绑定 | 企业、已有用户或车辆、角色/状态；服务端校验组织范围 |
| 有权限管理端 | 企业充值/余额查询 | 企业、充值金额分、`idempotencyKey`；返回余额与流水 |
| 企业管理端 | 策略设置/查询 | 单次与月度额度分、期望版本；返回生效策略 |
| 用户端 | 查询可用企业/车辆 | 不信任客户端用户 ID；返回当前登录用户有权使用的候选项及限制原因 |
| 用户端 | 企业付款预约 | 站点/电桩、`payerType`、企业、车辆、可选成本中心、`idempotencyKey` |
| 用户/管理端 | 企业订单与账单查询 | 授权范围、账期和分页；返回脱敏上下文、金额与对账状态 |
| 企业管理端 | 生成/确认月账单 | 企业、账期、`idempotencyKey` 或期望版本；返回账单摘要与行 |

现有预约请求可增加可选企业付款字段，但个人支付请求应保持向后兼容。服务端返回具体业务拒绝原因，例如企业冻结、成员停用、车辆不可用、无司机绑定、单次额度不足、月度额度不足、钱包可用余额不足、版本冲突或存在未结算订单。不得向客户端返回其他企业的数据来解释失败。

### 5.4 UI 范围

- 用户端：在预约确认页增加明确的“个人支付/企业支付”选择；企业模式下只显示已授权企业和车辆，并展示可用余额/额度提示及拒绝原因；个人模式保持现有默认行为。
- 管理端：平台视图提供企业创建、冻结和模拟充值；企业范围视图提供成员、车辆、绑定、默认额度、企业订单和月度账单。若现有客户端没有企业管理员登录域，可由具备组织范围的管理员页面承载，避免新建门户。
- 订单详情：展示付款类型、企业与车辆快照、企业钱包流水关联，但不泄露其他成员隐私。
- Web 企业看板不是 MVP 阻塞项；已有统一统计框架时可追加订单、费用、车辆活跃度和预算进度，并强制组织隔离。
- 企业支付失败不得自动切换并扣除个人钱包；如未来支持切换，必须由用户显式确认且仅能在开始充电前完成。

## 6 顺序实施步骤

必须按顺序实施。每一步均需提交可核对的产出并运行针对性验证；仓库已有能力应复用而不是复制。

### 步骤 1：仓库审计与最小集成设计

- 产出：现有鉴权/RBAC、预约事务、未结算拦截、钱包模型、计费结算、迁移和 UI 调用链说明；拟改文件清单与兼容个人流程方案。
- 验证：现有个人登录、预约、取消、充电和结算测试建立基线；能明确企业授权插入点、付款方锁定时机和事务边界。

### 步骤 2：企业、成员与组织隔离

- 产出：企业和成员建表、状态服务、平台创建/冻结、绑定现有用户、组织角色校验、分页接口和最小管理 UI。
- 验证：跨企业读取/修改被拒绝；冻结、暂停、离开和关闭前置条件测试通过；个人用户数据不受影响。

### 步骤 3：车辆与司机绑定

- 产出：车辆、司机绑定、状态管理、企业范围查询和用户端可用车辆查询。
- 验证：只能绑定同企业有效成员；非活动车辆/成员不能用于新预约；并发重复绑定由约束阻止；历史引用不可被物理删除。

### 步骤 4：企业钱包与充值

- 产出：通用钱包所有者扩展或最小兼容方案、企业钱包创建、模拟充值、余额/流水查询、幂等与审计。
- 验证：金额使用整数分；重复充值幂等；并发余额更新无丢失；个人钱包所有测试继续通过。

### 步骤 5：消费策略、订单上下文与企业预约

- 产出：默认单次/月度额度、集中授权服务、企业付款预约字段、不可变 `fleet_order_context`、服务端预估和 `budget_hold`。
- 验证：越权企业/车辆、冻结企业、无绑定司机、额度边界、钱包可用额不足、两个并发预占、重复预约和未结算拦截测试通过。

### 步骤 6：取消释放与企业结算

- 产出：预约取消/超时的幂等释放；实际金额与预占差额处理；企业钱包扣款、流水、预占消费、额度统计和订单 `PENDING_PAYMENT -> PAID` 的原子事务。
- 验证：低于/等于/高于预占、余额不足后充值重试、重复支付、并发结算、事务注入失败和取消重复释放均不破坏余额与额度；不会静默扣个人钱包。

### 步骤 7：月度账单与最小展示

- 产出：账单/账单行建表、幂等生成、确认、订单/流水对账查询，以及企业管理端账期列表与详情。
- 验证：合计等于账单行且匹配已支付企业订单；重复生成不重复计费；跨企业账单不可见；账单确认不改变余额。

### 步骤 8：全链路回归与交付

- 产出：自动化测试、可重复初始化/演示数据、协议和迁移说明、功能开关说明、演示脚本、已知限制。
- 验证：空库初始化和既有库升级通过；个人付款全链路、企业付款全链路、模块关闭场景和服务端异常场景均有回归结果。

## 8 Definition of Done

- [ ] 平台管理员能创建、冻结和解冻企业，并把已有手机号用户绑定为企业成员。
- [ ] 企业范围管理员能维护有效成员、车辆和司机绑定，所有查询和修改都经过服务端组织隔离。
- [ ] 企业预充值钱包使用整数分，充值、扣款和余额变化都有幂等流水及审计，不允许负余额。
- [ ] 司机预约时可显式选择企业和车辆；服务端重新授权并原子创建订单上下文与预算预占。
- [ ] 企业、车辆、付款钱包和策略快照在开始充电后不可静默改变，失败时绝不自动扣个人钱包。
- [ ] 取消/超时正确释放预占，企业结算原子处理实际金额、钱包流水、预占和订单状态，并可安全重试。
- [ ] 核心订单仍只使用统一状态；企业余额不足时订单保持 `PENDING_PAYMENT`，原未结算拦截继续生效。
- [ ] 能按企业和账期生成可对账月度账单，账单确认不修改余额或历史订单。
- [ ] 个人充电流程和个人钱包保持向后兼容，企业模块关闭时核心系统仍能运行。
- [ ] 单元、集成、权限、协议和回归测试通过；扩展建表脚本、演示数据、运行命令、演示步骤及未实现项均有交付说明。

## 9 风险与降级

| 风险 | 首选处理 | 无法按期完成时的降级 |
| --- | --- | --- |
| 现有钱包只支持用户 | 最小扩展为通用所有者并全面回归 | 建立薄的企业钱包适配层，但复用同一流水/事务组件，禁止复制结算算法 |
| 预算预估不准确 | 复用分时计价预览并保存计算口径 | 使用服务端配置的保守固定预占；结算时仍处理差额并明确展示 |
| 策略模型膨胀 | 仅实现企业默认单次/月度额度 | 不做成员级、站点、时段和成本中心组合规则 |
| 企业管理 UI 工期不足 | 在现有 PC 管理端增加组织范围页面 | 由平台管理员代管企业；不新建独立门户，但服务端隔离不能省略 |
| 月账单生成较慢 | 分页读取并在事务外聚合、短事务落库 | 首版仅支持单月同步生成并限制数据量，不影响结算主链路 |
| 冻结企业与存量订单冲突 | 冻结仅拒绝新业务，保留存量结算责任 | 管理端只允许充值和完成存量结算，禁止新预约 |
| 工期不足 | 优先组织隔离、企业钱包、付款上下文和结算 | 大屏、成本中心和高级分析延期，不能交付半成品后付费或发票入口 |

任何降级都不能省略服务端组织授权、付款方快照、整数金额、无负余额、事务、幂等、未结算拦截、数据隔离或个人流程兼容。
